## Calendar

`routes/calendar_routes.py` owns `/api/calendar` behavior: config, multi-account CalDAV CRUD, connection test, sync, local calendar CRUD, event CRUD, recurrence expansion, ICS import/export, quick parse, and user timezone offset handling.

`src.caldav_sync` owns CalDAV fetch/sync. `src.caldav_writeback` owns pushing local changes back to remote calendars. Calendar routes request those behaviors; they do not own CalDAV protocol details.

Runtime behavior:

- local default calendars are created lazily per owner with stable UUID5 candidates. Default creation remains inside the caller's transaction so a failed event write cannot leave an orphaned calendar; SQLite serializes the absent-row check with `BEGIN IMMEDIATE`, other backends recover insert races inside a savepoint, and renamed-owner ID collisions advance through deterministic slots. List-only callers explicitly commit the lazy default.
- route-level no-login calendar access normalizes empty owner values to `ODYSSEUS_FALLBACK_OWNER` or `owner@localhost`, so route-created calendar rows do not use the empty string as their storage owner;
- CalDAV account config lives in per-user prefs as `caldav_accounts`, with the legacy `/api/calendar/config` route reading/upserting the first account;
- recurring rules are expanded server-side, including compound recurrence IDs;
- RRULE expansion is capped and marks truncated responses;
- event datetimes preserve UTC/local metadata through `CalendarEvent.is_utc` where supported;
- CalDAV pull uses a bounded sync window, scopes existing UID lookups to the synced calendar, stamps account ids and remote metadata on local calendars, maps Google principal URLs to event collections, preserves locally-created or writeback-pending events that are not yet remote-owned, and deletes stale in-window remote events only when remote object parsing did not fail;
- CalDAV writeback stores `remote_href`/`remote_etag`, clears `caldav_sync_pending` only after successful remote writes, and leaves create/update/delete pending markers for retry on failure;
- pull and writeback paths always close their `DAVClient`, including discovery,
  database, and remote-write failure paths;
- sync direction can be pull, push, or both, and pending local writeback rows are included even before remote href metadata exists;
- ICS import is per-owner, capped, creates fresh local IDs in the target import calendar, and preserves zero-duration events as visible imported rows rather than dropping them as empty ranges;
- writeback is best-effort and local SQLite remains source of truth when remote writes fail.

Calendar credentials are encrypted at rest and are not returned to clients. CalDAV URL validation rejects unsafe schemes, credentials, fragments, localhost names, bad ports, unsafe IP literals, and hostnames resolving to disallowed addresses, with `ODYSSEUS_ALLOW_PRIVATE_CALDAV=1` as the explicit private-IP escape hatch. CalDAV sync/writeback clients disable redirects so credentials are not followed to another origin. The connection-test client keeps proxy/environment trust disabled but explicitly loads an operator `SSL_CERT_FILE` or `REQUESTS_CA_BUNDLE` when the file exists so private/self-signed deployments use the same CA trust intent as real sync.

## Tasks And Assistant Runs

`src.task_scheduler.TaskScheduler` owns scheduled task execution, next-run computation, strict single-slot execution, queued/running cleanup at startup, overdue next-run advancement, webhook-triggered tasks, notifications, run records, chained tasks, and event-triggered actions.

Cookbook serve scheduling crosses this domain. The Cookbook UI creates `cookbook_serve` scheduled tasks, can mirror them as Cookbook calendar events with `cookbook_event_uid`, and task deletion cleans up the linked event when present, falling back to exact-summary matching for legacy events without a stored UID. Cookbook command execution/lifecycle details stay in `cookbook-hwfit.md`.

`routes.task.task_routes` owns task CRUD, status, manual run/stop/cancel, pause/resume, owner-scoped run/activity history, metadata, onboarding defaults, cache clearing, parse endpoints, and webhook-token regeneration. `app.py` imports the canonical package path; `routes/task_routes.py` replaces its module entry with the canonical module for legacy import and monkeypatch compatibility. Chained-task `then_task_id` values are validated as same-owner relationships on create/update, and scheduler execution also rejects cross-owner or cyclic chains.

`src.tools.system.do_manage_tasks()` translates structured schedules: `day_of_month` is an integer 1–31 for monthly tasks, while recurring `weekdays` names plus `scheduled_time` in UTC `HH:MM` become a cron expression. Conflicting day/cron inputs are rejected. One-off `scheduled_date` values are parsed to naive UTC and must be future dates; recurring schedules reject supplied one-off dates, and invalid cron expressions are refused. A time-only edit of an existing five-field cron rewrites its minute/hour fields while preserving calendar fields and recomputes `next_run`; it does not merely update the legacy display clock.

Task webhook paths are auth-exempt at the app middleware layer only for `/api/tasks/{task_id}/webhook/{token}`. The route still validates active task state plus task-specific webhook token before dispatch.

Task runtime behavior:

- task runs move through queued/running/success/error/skipped/aborted states;
- scheduler/background execution can wait for `src.interactive_gate` to report a quiet foreground window, and running background work can use browser heartbeat/chat-stream activity as a cancellation/defer signal where implemented;
- output targets include chat sessions, notifications, email, and MCP delivery paths;
- LLM and research tasks can carry a built-in `character_id` persona prompt that the scheduler prepends at execution time;
- task-created chat sessions can be foldered under `Tasks`, and startup migration backfills task/research folders for legacy sessions;
- event-bus triggers persist counters and `next_run` before scheduler handoff;
- the in-process scheduler is gated by `ODYSSEUS_INPROCESS_TASKS`, and multiple enabled app processes can double-run work.
- action tasks with `run_local`, `run_script`, `ssh_command`, or
  `cookbook_serve` are admin-only. `routes.task_routes` enforces this on create/update/manual run and hides those actions from `/meta/actions` for non-admin owners; webhook and scheduler execution pause the task and clear `next_run` if an admin-only action belongs to a non-admin owner.
- background LLM task execution uses the background workload path, and the
  scheduler can abort/cancel active in-process task runs when foreground browser activity appears.
- `tidy_research` scans all persisted research files because broken JSON has no trustworthy owner stamp, so it runs only for admins or the explicit auth-disabled single-user operator and refuses regular/pre-setup callers before enumeration.

`routes.assistant_routes.py` owns crew/assistant settings and run-status surfaces that use the scheduler. `TaskScheduler.ensure_assistant_defaults()` currently seeds the personal assistant crew member and pinned assistant session, but no longer auto-creates Morning/Midday/Evening check-in tasks. Existing crew-linked check-in tasks are still rendered and managed when present.

## Notes And Reminders

`routes.note.note_routes` owns notes/todos/reminders, and `app.py` imports that canonical path. `routes.note_routes` replaces its module entry with the canonical module for legacy import and monkeypatch compatibility. Notes are SQLAlchemy `Note` rows and can include due dates, ordering, images, repeat state, AI classification, source/session provenance, and agent session linkage.

Notes CRUD/reorder/reminder routes resolve the acting owner through `require_user()`: auth-enabled anonymous requests fail closed before hitting owner-scoped queries, while documented no-login/single-user modes still resolve to the compatibility owner path.

### Note Content Model

A note is one markdown document, `Note.content`. Checklist items are GitHub-style task lines inside it and images are markdown images. `core/notes_markdown.py` owns the rules; it is stdlib-only so the migration, the routes, the agent tool and the CLI share it without import cycles.

Task-line grammar (`_TASK_RE`): optional spaces or tabs, a `-`, `*` or `+` bullet, one or more spaces or tabs, a `[ ]`, `[x]` or `[X]` box, then the item text to the end of the line. Nesting is two spaces per level, a tab counts as one level, and emitted lines are capped at three levels. Lines split on `\n` only (CRLF counts as one break), not `str.splitlines()`, so numbering agrees with the JS mirror.

Fence rule: a line opening with three or more backticks or tildes starts fenced code, and only a delimiter of the same character that is at least as long closes it (CommonMark). An unclosed fence runs to the end of the document. Task-looking lines inside a fence are code, not items: they are not numbered, toggled, counted for `note_type`, or treated as already present by the migration.

A task's index is its 0-based ordinal among task lines outside fences. `core/notes_markdown.py`, `frontend/src/features/notes/domain/markdownTasks.js` and the interactive task renderer in `static/js/markdown.js` all number the same way, pinned by `tests/fixtures/notes_task_vectors.json`, so a toggle by index means the same line in the API, the agent tool and the UI.

### Derived Fields And Write Compatibility

`content` is the source of truth; the API keeps its shape by deriving the legacy fields on read (`_note_to_dict`):

- `items` is `[{index, text, done, indent}]` from the task lines, or `null` when there are none (so a note written with `items: []` reads back `null`). An item's old `id` and any other key a client sent are not kept;
- `note_type` is `checklist` when the content is only task lines and blank lines, `note` otherwise. `goal` and `draw` are stored modes, not derived (`STORED_NOTE_TYPES`), so the Goals/Today views and drawings keep working;
- `image_url` returns the legacy attachment URL for any note type, including a drawing's canvas. Markdown-only images do not populate this field.
- `body_revision` is an opaque token for the body and its legacy fields. Use the token from the read that supplied the task index or editor contents.

Writers that still send the legacy fields are folded into content server-side, on `POST /api/notes` and `PUT /api/notes/{id}`:

- `items` rewrites the task lines in place (`apply_items_to_content`): the n-th item rewrites the n-th task line, an unchanged line is kept byte for byte, extra items are inserted after the last task line, task lines past the end of the array are dropped, and prose and fenced code are untouched. An item with blank text removes its task line, so the items read back are the array without it. An omitted `items` leaves the task lines alone;
- `image_url` identifies one legacy attachment. A new URL replaces its folded standalone line or adds the reference once. An empty string or `null` clears the attachment. Inline Markdown images and ordinary links keep their destinations.
- A `content` write with omitted `image_url` keeps the legacy attachment even when the payload contains only prose. Without `items`, it also keeps old task lines when the new text contains none. On REST PUT, `content: null` clears the prose, `items: null` or `[]` clears the checklist, and `image_url: null` clears the attachment. Omitted fields retain their compatibility behavior.
- Send `replace_content: true` with `content` to replace the complete document. Omitted task lines and images are removed. The server clears the compatibility attachment pointer if its image is absent. The text editor uses this mode for a Markdown document. A legacy field sent explicitly is still applied.
- Send the observed `body_revision` with body edits to reject a stale client edit with HTTP 409. PUT without a token remains available for older callers and conflicts if another body write commits after the server read.

Boot folds older rows on SQLite. Readers project unmigrated fields with `effective_content()`. The first body write folds readable legacy items and the image. Unreadable items survive unless explicitly replaced. See [the migration and rollback notes](../docs/notes-markdown-migration.md).

Clients that relied on persistent checklist IDs, custom item properties, the exact stored `note_type`, or a bodyless index toggle need updating. A mixed note takes the derived type `note` even when it contains tasks.

`content` with `items: []` writes the text without task lines, which is how a client clears a checklist; `content` with a non-empty `items` writes the text as sent and then rewrites its task lines from `items`. A `content` write with neither `items` nor `replace_content: true` (nor `base_updated_at`, which older note windows send with the whole document) keeps the note's existing task lines when the new text has none (`keep_task_lines`) and keeps the legacy attachment line: an API client or agent that edited the prose of a checklist note does not delete its tasks. The note window sends the whole document with `replace_content: true`, so its text is written as is, and a legacy attachment whose line it no longer contains is dropped.

That keeps the CLI, both calendar reminder writers (`routes/calendar_routes.py`, `src/tools/calendar.py`, which now write task lines through `items_to_markdown`), card edits and older API clients working unchanged. A row the boot migration skipped still has legacy `items` or `image_url`; readers use `effective_content()`, which folds both in on the fly (the REST payload, the `manage_notes` list and view, selected-notes chat context, the daily brief, both reminder builders and the CLI), and the first write through the routes or the tool folds them into the row (`fold_legacy_columns`). Unreadable `items` are left in place for the migration to retry. See [`docs/notes-markdown-migration.md`](../docs/notes-markdown-migration.md) for the migration and rollback.

### Checklist Endpoints

- `POST /api/notes/{id}/items/{index}/toggle` flips the done state of task line `index` in content, leaving indent, bullet and text as they were. Its JSON body must carry `body_revision` or `base_updated_at` from the read that supplied the index (`{"body_revision": "<token>"}`); a missing or stale token is 409 with the current note, because a positional flip computed from another version could tick another task. Read the note again and verify the intended task before retrying with its current index and token. Success returns `{ok, item, items, note}`; with a current token, a note without task lines or an out-of-range index is 400. The body may also carry `text`, the task's text as the client saw it (`find_task_index`): when the task at `index` still has that text it is flipped; otherwise the one task with that text is; when that task is gone or the text is now ambiguous, the answer is 409 with `detail = {"message": "That checklist item changed elsewhere", "note": <current note>}`. `done` sets the task to that state instead of flipping it.
- `POST /api/notes/{id}/items` with `{text, indent}` appends one open task after the last task line (or as a new block when there are none), so adding an item no longer PUTs the whole checklist. It needs no token, since it cannot overwrite anything: a lost race re-reads the committed body and appends again, up to `NOTE_WRITE_ATTEMPTS`, then 409. Empty text is 400. It returns `{ok, item, note}`.

The toggle and the append are re-applied to the newer row when another write lands first (see "Stale Writes"), so concurrent ticks and appends all count. Card checkboxes and the window send the task's text with the toggle and redraw from the note a 409 carries; the card's add-item input uses the append route. A card's item edit or removal sends `base_updated_at`; on a 409 the card takes the server copy and repeats the edit once on the item with the same text, and if that item is gone or ambiguous it keeps the server copy and shows "This checklist changed elsewhere. It has been refreshed."

### Note Images

Images are ordinary markdown images in content, `![alt](/api/upload/<id>)`, optionally sized `![](/api/upload/<id> "w=33")`. There is no image field beyond the legacy fold above.

- The note window's image button, a paste carrying image files and a drop of image files all upload through `POST /api/upload`; a multi-file drop is one request. Each image lands as its own block after the block holding the caret (at the end when there is none), and the note saves right away. Pasted or dropped text and HTML still go in as plain text.
- Tapping an image in an editable block opens a menu with S, M and L (`"w=33"`, `"w=66"`, no title) and Remove. A paragraph that Remove leaves empty goes too. When the body is not editable (a view-only window, Markdown source mode), tapping an image does nothing.
- Cmd/Ctrl+Z right after an insert removes the inserted images, until the next edit. The browser's own undo stack never sees the insert.
- `POST /api/upload` refuses with 429 once the same client address has uploaded three or more files in the last 10 seconds (`UploadHandler.max_concurrent_uploads`); one request can still carry several files. The window then shows "Image upload failed" (or "Some images could not be uploaded").
- Sketch opens the drawing canvas as a sheet in place of the body; "Insert sketch" uploads the PNG and inserts it like any other image.
- A card leads with the note's first image: card rendering takes the first `img.md-note-image` out of the rendered HTML and shows it cropped with the existing `.note-card-image` style. The other images are not shown on the card.
- A card renders only the start of its note (`previewSource()` in `ui/cardRendering.js`): the first 40 lines or 2,000 characters (`CARD_PREVIEW_MAX_LINES`, `CARD_PREVIEW_MAX_CHARS`), or for a checklist box the first 200 tasks (`CARD_CHECKLIST_MAX_TASKS`), followed by `…`. The source is cut at a line, so every shown task keeps its index, an open code fence is closed, and the note's first image is still used as the thumbnail when it lies past the cut. A save from the window or a re-read that changed one note redraws that card in place; the grid is redrawn only when the order changes, and the reflow animation reads every card's position before it moves any.
- Removing an image from a note does not delete the upload. Upload cleanup is not automatic: the admin route `POST /api/upload/cleanup` removes uploads that no stored row references and that are older than `cleanup_days` (30). An inline image in note content counts as a reference, sized or not.

The `manage_notes` `content` description gives models the same URL policy and the `"w=33"` / `"w=66"` syntax.

### Stale Writes

Every note payload carries two concurrency tokens: `body_revision`, a hash of the body fields (`owner`, `content`, legacy `items` and `image_url`, `note_type`; `core.note_writes.note_body_revision`), and `updated_at`. A `PUT /api/notes/{id}` that writes the body (`content`, `items`, `image_url` or `note_type`) and every checklist toggle must send one of them back, as `body_revision` or `base_updated_at`. A body write with neither, or with either one stale, is refused with 409 and `detail = {"message": "Note changed. Reload it and retry." (NOTE_BODY_CONFLICT), "note": <current note>}`, so the client can offer the newer copy instead of overwriting it. `body_revision` ignores metadata changes made meanwhile (pin, colour, order, tags); `base_updated_at` asks for exactly the version the client showed. A `PUT` that only changes metadata needs no token.

Every note write is a conditional update (`core/note_writes.py`): `UPDATE … WHERE id = ? AND updated_at = ?`, with the stamp read before the row is loaded, so two writers can no longer both pass the check and have one silently overwrite the other. A body write also runs `guard_note_body` right before that commit, which checks the row still holds the body the write was computed from (a migration can change the body without moving `updated_at`) and takes the write lock; calling it earlier would hold SQLite's lock for the whole request. A `PUT` with `base_updated_at` that loses that race gets the 409 above. A `PUT` with `body_revision` only, a metadata-only `PUT`, a toggle with `body_revision` and an append are re-applied to the newer row, re-checking the token, up to `NOTE_WRITE_ATTEMPTS` (5) times, then 409. `POST /api/notes/{id}/versions/{vid}/restore` takes either token optionally.

### Size Limits

Every string a note stores has a limit, in characters (`src/constants.py`): `NOTE_CONTENT_MAX_CHARS` (1,000,000) for `content`, `NOTE_TITLE_MAX_CHARS` (1,000) for `title`, `NOTE_LABEL_MAX_CHARS` (1,000) for the tags (`label`), and `NOTE_FIELD_MAX_CHARS` (512) for each of `color`, `due_date`, `repeat`, `note_type`, `source`, `session_id`, `gallery_id` and `agent_session_id`. `core.note_writes.size_refusal()` checks the fields as the write would leave them, and refuses a field past its limit only when the write makes it longer than it was, so a note stored before the limits can still be trimmed, ticked and edited down. `POST` and `PUT /api/notes`, and the checklist append, answer 413 with `detail = {message, field, length, limit}` and save nothing; `manage_notes` (and so the Codex todo bridge) returns the same message as an error. The note window shows the message with "Shorten it to save. Your edits are kept on this device." until an edit brings the note back under the limit (`sizeRefusal` in `domain/noteRules.js`), and a card's checklist edit shows it as its error.

### Note Versions

`core/note_versions.py` keeps each note's earlier versions in `note_versions` (`NoteVersion`: `note_id` with a foreign key to `notes.id` `ON DELETE CASCADE`, `owner`, `created_at`, `source` `agent`, `user` or `restore`, `session_id` for an agent edit, `author` for the account that saved, `fields` and a `digest`). The table is created by `create_all`. A version is the note's `UNDO_FIELDS` (title, content, items, colour, tag, pin, reminder, type) exactly as stored just before a change, written in the same transaction as the change:

- before every agent write through `manage_notes` (`update`, `toggle_item`), from a chat started from the note or from any other chat;
- before a save of the user's (the note window, a ticked task, an added task) when the latest version is older than `NOTE_VERSION_USER_GAP_SECONDS` (10 minutes), was not a save of the user's, or was another person's, so typing keeps one version per pause;
- before a restore and before the agent Undo, so either can be undone.

A write that leaves those fields as they were keeps nothing. A note keeps at most `NOTE_VERSIONS_MAX` (50) versions and `NOTE_VERSIONS_MAX_CHARS` (10,000,000) characters of them (the stored `fields`), oldest dropped first, except the newest and, for each `author`, their newest version and the one after it (the note as their last save left it); until the owner has a version of their own, the oldest version (the note as created) counts as theirs. Those can take a note past either limit, by at most two versions per author. Every delete path (the route, `manage_notes delete`, calendar reminder cleanup, account purge, admin wipe) deletes them with the note.

Owner only; a collaborator gets 403, and a collaborator's edits are versions in the owner's history under their name:

- `GET /api/notes/{id}/versions` lists versions newest first without their full text: a preview, `summary` (who made the change and what it did, computed when the list is read from each version and the next newer one, the note itself for the newest), `chat_title` and `chat_exists` for an agent version (the owner's chats only).
- `GET /api/notes/{id}/versions/{vid}` returns one version in full.
- `POST /api/notes/{id}/versions/{vid}/restore` takes `base_updated_at`, answers 409 with the current note when the note moved on before or during the write, and 409 when an upload the version shows has been deleted (the reservation rule every write follows). Its response carries `undo_version_id`, the version the restore kept.

The owner's note payload carries `version_count`.

### Note Sharing

A note has one owner, `Note.owner`, and any number of collaborators, one `NoteShare` row each (`note_shares`: `id`, `note_id` with a foreign key to `notes.id` `ON DELETE CASCADE`, `shared_with` as a lowercased username, `permission` `view` or `edit`, timestamps; unique index `ux_note_shares_note_user` on `(note_id, shared_with)`). The table is created by `create_all`; nothing in `notes` changes. `core.notes_sharing.note_access()` is the one place that turns this into capabilities, and the routes and the agent tool both ask it:

| Caller | read | write (content, title, tasks) | manage (pin, archive, order, delete, owner-only fields) | share |
| --- | --- | --- | --- | --- |
| Owner | yes | yes | yes | yes |
| `edit` collaborator | yes | yes | no | no |
| `view` collaborator | yes | no | no | no |
| Anyone else | no | no | no | no |

Access checks (`note_access`) and grants compare usernames trimmed and lowercased, and `""` and `None` are the same "no user" value. Listing the caller's own notes (`GET /api/notes`) and the owner side of an account rename match `Note.owner` exactly as stored.

Owner-only fields (`OWNER_ONLY_FIELDS`): `pinned`, `archived`, `sort_order`, `agent_session_id`, `color`, `label`, `due_date`, `repeat`, `note_type`, `gallery_id`. A collaborator's `PUT` that sets any of them is refused with 403 `Only the note's owner can change: <fields>`; `/pin`, `/archive` and `DELETE /api/notes/{id}` need `manage`.

Status codes (`_load_note`): a caller without read access gets the same 404 `Note not found` as a missing note, so the routes are not an existence oracle. A `view` collaborator who writes gets 403 `This note is shared with you as view only`; a collaborator asking for `manage` or `share` gets 403 `Only the note's owner can do that`.

`GET /api/notes` returns the caller's notes, then, in the active view only, the active notes shared with them, plus `me` (the caller's username). The response carries a strong `ETag` over its exact body (`Cache-Control: private, no-cache`), and a request whose `If-None-Match` names it gets 304 with no body; the tag changes whenever anything the caller would see changes, including a collaborator's edit or a deletion. Every payload carries `is_owner`, `shared_by`, `my_permission` (`owner`, `edit` or `view`), `can_edit`, `is_shared` and `shared_with`. The roster, `shared_with`, goes to the owner only: a collaborator learns who shared the note and their own permission, never who else has it. A collaborator's copy also has `session_id`, `agent_session_id`, `ai_classification` and `ai_content_hash` nulled.

Routes:

- `GET /api/notes/share-targets` (`can_share_notes`) answers `{users, directory}`. For an admin, `users` lists the other accounts' usernames and `directory` is true. For anyone else, and in single-user mode, `users` is empty and `directory` is false: they share by typing the exact username, and the popover shows a username field in place of the list. It is declared before `GET /{id}` so the literal path is not read as an id.
- `GET /api/notes/{id}/shares` (owner) returns `shared_with`.
- `POST /api/notes/{id}/share` with `{users, permission}` (owner, `can_share_notes`) upserts grants: sharing again with another permission flips it. Names are trimmed and matched without regard to case. A name no account has refuses the whole request with 404 `No account with that name` (`NO_SUCH_ACCOUNT`) and writes nothing; the note is checked first, so on a note the caller can't share the answer is the usual `Note not found`. The owner and blanks are skipped. It returns `shared`, `skipped` and the new `shared_with`. A permission other than `view`/`edit` is 400, and an unreadable account list is 503. The 404 still tells a caller whether a name they guessed is an account; that is accepted for now, since the list itself is no longer handed out.
- `DELETE /api/notes/{id}/share/{username}`: the owner removes anyone; a collaborator can remove only themselves, which is how they leave a note (`left: true`).

`GET /api/notes/{id}/media/{upload_id}` serves an upload to anyone who can read the note, only when the note's content references that upload, and only when the upload belongs to the note's owner or a current collaborator; anything else is 404. It serves images only: PNG, JPEG, GIF, WebP, AVIF and BMP inline (`NOTE_MEDIA_INLINE_TYPES`), SVG as an attachment (`NOTE_MEDIA_ATTACHMENT_TYPES`, so an `<img>` still shows it but opening the URL downloads it), and every other type is the same 404, always with `nosniff`. A collaborator's images stop loading through the note once they leave or are removed; the owner can insert their own copy. `/api/upload/{id}` stays owner-only, so on a shared note the renderer (`opts.mediaNote`) rewrites each `/api/upload/<id>` image to the note-scoped path. Only the rendered `src` changes: stored markdown keeps `/api/upload/<id>`, and the serializer writes it back that way. Read access to a note therefore never reaches an upload the note does not show.

Writes reserve only the uploads they add (`_reserve_new_note_uploads`), read from the note as it will be stored (`_note_upload_refs`: content with any legacy fields folded in, plus `image_url` and `color`), not from the request fields, on create, update and append and in `manage_notes` `add` and `update`. Uploads already in the note were reserved by whoever inserted them, possibly the owner or another collaborator, so re-reserving them as the writer would refuse every save. One edge remains: if someone removes an image another account uploaded, saves, then restores it and saves again, that save is refused with 409, because the image counts as new.

Deleting a note deletes its grants. The route, `manage_notes delete` and calendar reminder cleanup (`_delete_calendar_reminders_for_event`) delete them explicitly (`delete_note_shares`) as well as through the cascade; the admin wipe and `scripts/odysseus-notes delete` rely on the `ON DELETE CASCADE` foreign key alone, which SQLite enforces because the engine turns `PRAGMA foreign_keys` on for every connection. Renaming an account re-points its grants in the rename transaction (`rename_shared_user`); when the new name already holds a grant on the same note, the two merge and keep `edit` over `view`, and a grant on a note the new name owns is dropped. Deleting an account deletes the notes it owns. Before the account is removed, the admin delete route checks the deletion is allowed (`can_delete_user`) and calls `purge_notes_owned_by()`, which in one transaction removes every note whose trimmed, lowercased `owner` is the account, their grants (explicitly and through the cascade) and their `note_legacy_fields` rows, so the migration rollback cannot bring them back, plus every grant naming the account on other people's notes. Notes with `owner IS NULL` and other accounts' notes are never touched, an empty name deletes nothing, and a second run finds nothing and returns zeros. Collaborators lose the deleted notes. If the purge fails, it rolls back, the account is kept and the route answers 500 "The account's notes could not be removed, so the account was kept. …", which the admin UI shows; retrying is safe. If the purge succeeds and `delete_user` then fails, the notes are gone and the account stays (400); deleting again finishes the job. A successful deletion answers `{"ok": true}`. Uploads the notes referenced are not deleted; they become unreferenced and go with the next admin `POST /api/upload/cleanup` once older than its 30-day cutoff.

Single-user mode (no account boundary: auth disabled, loopback bypass, or unconfigured first run, where `require_user()` resolves no user) has nothing to share: every note stays fully accessible as before, `share-targets` is empty with `directory: false`, and `POST /share` answers 400 `Sharing needs signed-in accounts`.

`can_share_notes` is a default privilege (`core/auth.py:DEFAULT_PRIVILEGES`, on for every account; admins always have it), shown as "Share notes" under Settings → Users. It gates `share-targets` and `POST /share`; removing people and leaving do not need it.

Reminders stay the owner's: the scheduler's note scan and `/fire-reminder` only fire for the owner, and the browser reminder loop, due badges and "Clear past" count only the caller's own notes. A note shared with the caller still carries its owner's `due_date`, but its card never glows or pulses for it (`_hasActiveReminder()` is false on a note that is not mine).

### Note Rendering

Note cards and the note window render content with `mdToHtml(content, {tasks: 'interactive', images: 'notes', dialect: 'notes'})` (`_renderNoteMarkdown` in `frontend/src/features/notes/index.js`). Only Notes passes these options: the note window adds `sourceMap: true` (see "Notes Frontend State And Lifetimes"), and the chat's note context cards render with `images: 'notes', dialect: 'notes'` and static task boxes. Rendered task rows also get the existing `.note-checkbox` classes, so the card, mobile and select-mode handlers apply to them unchanged.

- `tasks: 'interactive'` numbers task lines on the raw source with the fence rule above, before any other pass, and renders them as `li.md-task[data-task-index]` rows with a `role="checkbox"` box. A task line that lands where a list cannot render (inline code, a `<details>` block) keeps its text but is not clickable.
- `images: 'notes'` loads images from this origin only: an `/api/upload/<id>` path, a base64 `data:image/` PNG, JPEG, GIF, WebP or SVG URL (as an `<img>`, SVG runs no script and loads nothing), or a same-origin `blob:` URL (`noteImageSrc`). An upload written with another host in front (`http(s)://<old host>/api/upload/<id>`, no query or fragment, `noteUploadElsewhere`) loads from this server by its path and the other host is never contacted; once it has loaded, the next edit saves its path only (`ui/noteImages.js`), and one this server does not have keeps its address as written. An image whose file is missing shows a frame with its alt text, or "Image not found" (`.note-image-missing`, `ui/noteImages.js`), whose menu still edits or removes it; nothing about the frame is written back. Any other markdown image renders as a plain link, unless the viewer turned on "Show external images in notes" (Settings, Appearance; the per-user pref `notes_show_external_images` through `/api/prefs`, read by `application/externalImages.js`, off by default). With it on, an `https:` markdown image (`noteExternalImageSrc`) renders as an image in the window, the cards and the chat's note cards, with `referrerpolicy="no-referrer"`, `loading="lazy"` and no `crossorigin`; `http:`, protocol-relative and other schemes stay links, and raw HTML `<img>` is never opted in: the renderer marks the images it built with a per-render nonce (`data-ody-external`) that `scrubNoteHtml` checks and removes. The setting is the viewer's, so a collaborator who keeps it off never fetches an image the owner embedded, and the note window reads it once when it opens. What is saved is the same either way. Raw HTML that survives the allowed-HTML sanitizer can still name a resource, so the rendered markup is parsed on an inert `<template>` as the last notes pass (`scrubNoteHtml`, after the dialect's escapes are restored) and cleaned: a `src` that is not a notes image source is removed, as are `srcset`, `poster`, `background`, `ping` and `xlink:href`, and a `style` that names any URL-taking CSS function (`url(`, `image-set(`, `image(`, `cross-fade(`, `element(`, `src(`, `paint(`, `@import`, `expression(`, matched after CSS escapes are decoded) is dropped whole. With the external images setting off, displaying a note therefore never makes the browser fetch a third-party URL, whoever wrote the note; with it on, only the `https:` markdown images above are fetched. This is the notes policy only: chat messages render with the default renderer (`imageHtml` in `static/js/markdown.js`), which does load external markdown images.
- The same pass removes every `on*` attribute and keeps a link target (`href`, `xlink:href`, `action`, `formaction`) only when it is `http`, `https`, `mailto`, `tel`, a path or an anchor (`NOTE_LINK_SCHEMES`), so an escape such as `javascript\:` cannot carry a scheme past the sanitizer. In the note window a plain click or a tap on a link opens it in a new tab (`noopener,noreferrer`), only when its target passes the link menu's check (`normaliseLinkUrl`); a drag, a click that leaves a selection and a Shift or Alt click stay edits, and the caret gets into a link with a click beside it or the arrow keys, where Cmd/Ctrl+K opens the link menu. An image shown as a link chip opens on Cmd/Ctrl+click only, so a stray click never loads it.
- `color` is one of the palette names (`NOTE_COLORS`: red, orange, yellow, green, blue, purple; the same list as `COLORS` in `ui/colors.js`), empty for none, or `bg:/api/upload/<id>` for a picture background (`normalize_note_color`). A `bg:` value with an `http(s)` origin in front, as older clients wrote it, is stored as the bare path. Anything else is 400 from the routes, a tool error from `manage_notes` and a non-zero exit from the CLI. Cards turn only a palette name into a class and only an upload path into a style, so a value stored before this check is ignored.
- A note image's title `w=N` is its width in percent of the note, clamped to 5..100 and rendered as `data-w` plus an inline width (`noteImageSize`); 100 writes nothing, and any other title stays a title. Note images get `class="md-note-image"`, `loading="lazy"` and `decoding="async"`.
- `dialect: 'notes'` is what the note editor writes back. A backslash escapes one markdown character (`` \ ` * ~ # - + . > | $ < _ ! [ ] : ``), so typed `2 \* 3 \* 4` stays text; code spans and `\[ … \]` / `\( … \)` math keep their backslashes. Indented `- ` and `* ` bullets nest (two spaces per level, up to three), and an ordered list that starts at a number other than 1 keeps it as `<ol start>`.

Reminder policy:

- "remind me at 5pm" should become a todo/note with a due date;
- calendar event alarm/reminder UI writes reminder Notes;
- calendar events are for scheduled time blocks, meetings, appointments, or explicit calendar requests;
- creating a calendar event named "Reminder" does not create notification behavior.

Built-in reminder/persona prompt text is mirrored server-side for reminder synthesis and scheduled task execution; frontend persona selectors are UI over that server-owned id map, not the authority.

Reminder dispatch is Note-owned:

- `dispatch_reminder()` owns browser, email, ntfy, generic webhook, in-app notification, optional LLM reminder text, and dedupe behavior;
- the scheduler note scanner calls note-ping actions for backend due-note delivery with per-owner notification state, and calendar-event reminders are treated as Note-owned reminders rather than separate scheduler event pings;
- the notes frontend has a browser-tab fallback for visible sessions;
- calendar frontend reminder UI stores reminder records as Notes, not calendar-event notification jobs.

Reminder text comes from one builder, `core.notes_markdown.reminder_body()`, shared by `/api/notes/fire-reminder` and the scheduler's `action_ping_notes()`: the note's prose with task lines removed (first 400 characters), then `Pending (N):` and up to eight open tasks as `- text` lines, with `...and K more` past that. A note with tasks but none open gets its prose, or `N items`; a note with no task lines gets its first 400 characters. The text is plain words (`reminder_text()`): image markdown is dropped, a link becomes its text, heading and quote markers go, fenced code stays as written, and a task that is only an image is not listed. The browser's local notification follows the same rules (`reminderBody` in `domain/noteRules.js`), and both are pinned by `tests/fixtures/notes_reminder_vectors.json`. The synthesis filter that drops an echoed "Pending" line matches `Pending (N):`. The daily brief (`action_daily_brief()`) lists up to three open tasks from any note with task lines, not only `note_type == "checklist"`, and skips the calendar's own reminder notes, which its Calendar section already covers.

Email/ntfy failures degrade into channel result fields rather than blocking every reminder path. ntfy and generic webhook reminder URLs run through outbound URL safety checks, with `REMINDER_WEBHOOK_BLOCK_PRIVATE_IPS` controlling whether private/LAN targets are allowed. ntfy notification titles are converted to ASCII with replacement and capped at 200 characters before entering HTTP headers. Reminder dedupe uses owner-scoped cache files under `data/`.

`src.builtin_actions.action_ping_notes()` counts delivery only when `dispatch_reminder()` reports success for the configured browser/email/ntfy/webhook channel. Typed receipts in `data/note_pings_<owner-slug>.json` record time and channel. A browser fallback or legacy timestamp does not prove external delivery: the next eligible scan retries the configured external channel without queueing the recent browser fallback again. The scanner reloads dispatcher-owned receipts before pruning so it cannot replace a successful channel receipt with a timestamp; total delivery failure is not checkpointed. Retries occur only within 90 seconds of the due time, while recent matching-channel receipts suppress delivery for 25 minutes. Existing retry tests cover webhook/ntfy failures, legacy receipts, browser dedupe, total failure, and receipt-preserving pruning; live channel delivery remains separate validation.

## Agent, Codex, And CLI Surfaces

`do_manage_tasks`, `do_manage_notes`, and `do_manage_calendar` own agent-side writes. `do_manage_calendar` supports batch event creation plus list range aliases (`start`, `start_time`, `start_date`, `range_start`, `from`, `dtstart`, `since`, and matching end aliases), calendar name/short-id lookup, importance/tag aliases, and reminder offsets expressed as numbers, minute/hour words, or common abbreviations such as `min`/`mins`/`hr`/`hrs`. If a model supplies a loose `query`, `date_range`, or `range` without explicit start/end datetimes, `list_events` returns an error asking the caller to resolve the range and call again instead of guessing. Event classification reads `Memory.text` for personal context before LLM classification. `src.tool_index` encodes the reminder policy that notes/todos own reminders while calendar events own time blocks.

Agent native tool owner handling is not uniform today. `do_manage_tasks()` filters lists only when `owner` is truthy and creates tasks with the passed owner, so `owner=None` can create legacy/null-owner tasks. For authenticated/non-empty owners, edit/delete/pause/resume/run require an exact stored owner match and reject both cross-owner and null-owner rows; `owner=None` retains single-user compatibility. `do_manage_notes()` list/query behavior distinguishes `None` from `""`, with `None` acting as broader single-user compatibility while `""` filters to empty-owner rows in some paths. `do_manage_calendar()` query helpers filter only when owner is not `None`, while calendar creation routes through the calendar fallback owner for default calendars. These are compatibility behaviors, not a cross-user sharing model; note sharing is the explicit grant model described under "Note Sharing".

`do_manage_notes()` reads task lines from content. `get` (aliases `view`, `read`, `show`, `open`) prints each item as `[x] i: text` with the index `toggle_item` takes, and those aliases count as reads in `src/tool_capabilities.py` and `src/clean_agent_preview.py`. `list` stays a locator and does not print bodies. `toggle_item` needs an explicit integer index and `body_revision` from the same get/view result. It accepts an optional boolean `done`. On a conflict, read and verify the item before retrying. The Codex bridge translates these conflicts to HTTP 409. Explicit nulls on tool update body fields retain the previous behavior of leaving their values in place. To create or replace a checklist the tool still takes `checklist_items` (written into content through `apply_items_to_content`), because that path carries the validation for empty lists and tasks in titles; content the model writes may contain task lines directly. An `update` with `content` and no `checklist_items` keeps the existing task lines when the new text has none, and `checklist_items: []` clears them; the Codex todo bridge goes through the same code. The tool remembers the version of each note it last showed or wrote, and a `checklist_items` write over a newer version is refused ("This note changed since you last viewed it … Nothing was saved."), so tasks a person added during a run are not dropped; a run that never viewed the note is not checked. An `update` may carry `body_revision`, and a stale one saves nothing. The tool's `update` and `toggle_item` commit conditionally like the routes (`guard_note_body`, then the compare-and-swap), and a lost race saves nothing and is reported as a conflict. Selected-notes chat context (`_format_selected_notes_context()` in `routes/chat_routes.py`) sends the content verbatim plus an `Items:` block restating the tasks, with the derived `note_type`. `scripts/odysseus-notes` derives `items` and `note_type` the same way, and `create --item TEXT` (repeatable) writes task lines.

Note and calendar route/tool writers owner-reserve any canonical internal upload references in content, checklist/color/image fields, descriptions, and locations before their database writes. Missing or wrong-owner uploads fail the write instead of creating a dangling durable reference; reservations serialize with upload cleanup.

Chat forwards browser timezone offset and IANA timezone name so natural-language note/calendar tools can anchor dates to the user clock. A valid IANA zone wins over the fixed offset for current-time/DST reasoning; invalid or absent names fall back to the offset and then server-local/UTC compatibility behavior. Chat can auto-promote note/calendar/reminder intents to agent mode.

Sharing is a human action in the Notes window, never a model's. `manage_notes` has no `share`/`unshare` action and no `users`/`permission` arguments, and `share`, `unshare` and `leave` in any spelling are refused before the database is opened with `SHARING_UI_ONLY_ERROR` ("Sharing is changed from the Notes window: ... Nothing was changed."). The Codex todo bridge refuses the same three with 403 and that text for every token, before its scope check, so they never reach `manage_notes`; they are not in `WRITE_ACTIONS`, and `/capabilities` does not list them. The reasoning is in the `core/notes_sharing.py` module docstring: sharing discloses a private note to another account, so it should be a deliberate click by the owner, and notes, pages, emails and documents are untrusted input, so a prompt-injected one must never be able to get a note shared. `list` and `get` still show sharing (`shared by X, you can edit`, `shared with bob: edit`). Note ids and 8-character prefixes resolve only among notes the caller can read, an exact id first and then the caller's own notes, so a shared note never shadows one of theirs; `%` and `_` in a prefix are literal. A missing note and someone else's note give the same `Note '<id>' not found`, and a collaborator cannot set the owner-only fields the tool accepts (`pinned`, `archived`, `color`, `label`, `due_date`, `note_type`).

Agent runs started from Notes (`application/agentActions.js`) may edit the note they were started from, and no other. Three entry points share `runNoteAgent()`: the whole-note run ("Agent: solve this", "Re-run agent" once the note has a run) at the top of the window's Ask popover (the card menu lists it too, in the card action row the cards keep hidden), a per-item button on each open task row that opens the Ask popover about that item ("Agent: help with this" first, then the presets worded for the item and a typed request; nothing starts until one is picked), and the window's "Ask about this note" (four presets or typed text). Each creates a session named `Agent: <label>` on the default chat model with `note_id=<the note>` (and, for a per-item run, `note_focus_task=<row text>`), links the note to it through `agent_session_id` (saved before the run starts), and posts to `chat_stream` in agent mode, draining the stream in the background.

The edit scope is server state (`core/note_agent_scope.py`). `POST /api/session` with `note_id` checks the caller owns the note (404 otherwise) and stores it as `sessions.note_scope_id`, with the per-item run's todo as `sessions.note_focus_task` (one line, at most 2000 characters; 400 otherwise, or without `note_id`); every turn in that chat, follow-ups typed in the normal chat included, reads both back and binds the scope for its tool calls. Every such turn runs in agent mode, whatever the composer's toggle sends, so a typed follow-up, or a typed answer to an approval card, keeps the note's tools, scope and todo. Such a turn is always offered `manage_notes` (`always_available_tools` of its turn contract) and its request authority carries a `manage_notes` grant with the notes owned scope, whatever else the request is about; disabled tools and policy still apply. The client never names the note a turn may change. In such a chat `manage_notes` reads (`list`, `search`, `view`) any note as usual; `update` and `toggle_item` work on the scoped note only (an update without an id means that note): its title, content, tasks, colour, tag, pin, reminder and type; `add`, `delete`, archiving and any write to another note are refused with a tool error naming the note. A write must be based on the version the run last read (the note shown with the turn, a `view`, or its own previous write): otherwise it is refused with "The note changed since you last read it … Read it again", the `updated_at` rule the note window follows, so a run never overwrites what the user saved meanwhile. On a note with at least one collaborator every write asks through the tool approval prompt, whatever else the run has seen; a private note gets no prompt until the run reads untrusted content other than that note (a web page, an email, another note, another tool's output, or a taint carried over from an earlier turn with no known source), after which each write to it asks too; reading the chat's own note back (`view` by its id) is never held, since the run already has it (`_note_edit_scope_decision()` in `src/tool_capabilities.py`).

Before each agent write the fields a run may change (`UNDO_FIELDS`: title, content, items, colour, tag, pin, reminder, type) are stored as written in `notes.agent_undo`, with a digest of what the agent wrote; consecutive writes from the same chat keep the first snapshot. The owner's payload carries `agent_edit: {at, session_id, undoable}` (stripped from a collaborator's copy). `POST /api/notes/{id}/agent-undo` (owner only) puts the stored bytes back while the note still holds exactly what the agent wrote, and answers 409 with the current note otherwise. Each agent write's `tool_output` event carries `note_edit: {note_id}`; the drained run hands it to `application/agentEdits.js`, which re-reads the note, updates its card and the open window (unless the window has unsaved typing, whose save then meets the usual conflict), and shows "Agent edited this note" with Undo once per edit. The list re-read announces edits made from the chat. The window's meta line shows "Agent edited <time> · Undo" while the edit is undoable.

The note itself never goes into the user turn. The client sends `selected_note_ids=[<id>]`; the server loads the note with the caller's own access and adds it, with the session's todo as `Focus todo: …` on every turn of the chat, inside the selected-notes untrusted-context wrapper (`selected_notes_context_message()` in `routes/chat_helpers.py`). A `note_focus_task` sent to `chat_stream` is ignored. The wrapper arms the tool gate only when one of its notes has a collaborator: then a read or write the model asks for waits for the user's approval, and an edit collaborator's text cannot steer the owner's tools unseen. A note nobody else can open is the owner's own text, so it is fenced as data but arms nothing, and the run reads notes without a prompt. The owner's skills index, which every agent turn carries, is control-plane context like the skills block: it leaves reads open and still holds writes (`_CONTROL_PLANE_CONTEXT_SOURCES` in `src/tool_capabilities.py`). The window saves pending typing first, so the server reads what is on screen. The user turn is only the request:

- per item: `Help me with the focus todo of the attached note. The note is attached as the selected note.`;
- Ask: the request, then `The note is attached as the selected note.`;
- whole note: `Help me get this note done. The note is attached as the selected note.`;

each followed by `You may edit the attached note (and only it); other notes are read-only.` The notice names no tool on purpose: a tool name in the user turn narrows the turn's tools to that family, so an Ask such as "add this to my calendar" would lose the calendar. The selected-note context names the note's `Id:`.

Every run re-points `agent_session_id`, so a note links to its latest run; earlier sessions stay in the chat list. Agent runs are the owner's: they need a saved note the caller owns, and the agent affordances are hidden on notes shared with the caller.

Codex todo/calendar wrappers enforce bearer-token owner and `todos:*` or `calendar:*` scopes, then delegate to note/calendar behavior as the token owner. Normal calendar/task/note routes are current-user/cookie routes and should not be treated as scoped bearer-token APIs unless they explicitly use token owner/scope policy.

Direct DB CLIs are local compatibility tools. They bypass HTTP route behavior, CalDAV writeback, and some owner/timezone parsing policy.

## Event Bus

`src.event_bus` owns event-triggered task counters and scheduler handoff. Current emitters include chat/session/document/memory/research/email/skill paths. Ownerless events resolve to a primary configured user instead of broadcasting to every owner.

The current event bus is not a calendar-event emitter despite the adjacent calendar/task/reminder domain.

## Timezone And Date Semantics

- calendar events store offset-aware input as UTC/naive fields plus `is_utc`;
- note `due_date` uses ISO-like strings interpreted through note/tool parsers;
- chat forwards browser UTC offset into `routes.calendar_routes` request-local state for natural-language date anchoring in calendar/note tool parsing;
- generic scheduled task clock times are stored as UTC values after local conversion;
- assistant check-ins can use an IANA timezone on `CrewMember`, with UTC fallback.

Dateutil fallbacks strip timezone-aware parser results back to the naive-UTC contract before recurrence/window comparisons. Calendar agent list tools accept current range aliases implemented by `src.tool_implementations`, and equal/same-day start/end ranges are normalized to a one-day window instead of silently returning no rows.

Natural-language parsers prefer time-first interpretations for short reminder/event phrases where the user supplies a clock time before a date phrase.

Calendar frontend week-start preference is browser-local (`cal-week-start`) with Monday/Sunday controls; it is not persisted as a server preference.

Natural-language date parsing and timezone behavior are compatibility-sensitive and need route/tool/frontend regression coverage when changed. Request-local timezone context is ephemeral and must not be persisted as user state. A valid browser IANA timezone is authoritative over a possibly stale or wrong-sign fixed offset because it carries daylight-saving rules.

## Degraded And Optional Behavior

- CalDAV sync no-ops with shaped errors when unconfigured, invalid, offline, or missing the optional `caldav` dependency.
- CalDAV writeback failures are non-fatal to local calendar writes and are mostly visible through logs.
- Missing or invalid `croniter` rejects cron schedules or yields no next run.
- Missing timezone support falls back to UTC or legacy behavior.
- ICS import depends on `icalendar`; missing dependency can fail before route-shaped error handling today.
- Notes reminders can still use local browser fallback when backend email/ntfy channels fail.
- App backup import/export does not currently include calendar events, scheduled tasks, task runs, or notes; calendar ICS import/export is separate and calendar-only.

## Security And Provenance

Calendar, task, note, and assistant routes are owner-scoped for normal users. Notes add one explicit exception: a `NoteShare` grant from the owner gives another account read, or read and write, on that note only. Legacy null-owner behavior is compatibility-sensitive and should not silently grant authenticated owners broad mutation rights.

Because auth-disabled chat owners can arrive as `None`, tool-created rows may not use the same owner value as route-created rows. Multi-user or owner-model changes must audit both route and agent paths.

Task creation/update/manual run/webhook/scheduler execution blocks shell-like and Cookbook serve action types for non-admin users through `src.task_action_policy`, and tool security blocks privileged task/calendar tools for non-admin use. Assistant defaults reject synthetic owners such as `api` and `internal-tool`.

Note routes store caller-provided `source`, `session_id`, and agent-session provenance; a caller-provided `image_url` is folded into content as a markdown image, and `color` is validated against the palette (see "Note Rendering"). Canonical internal upload references in persisted note/calendar fields are owner-reserved before writes, and upload-backed bytes remain protected when fetched through upload routes. Arbitrary non-upload image URLs in content are not otherwise normalized or validated by note storage; the boundary is at display, where the notes image policy above refuses to load anything that is not same-origin.

## Calendar Reminder And Invitation State

Calendar event responses now include reminder note id, due time, minutes-before, and source-email provenance. Create/update accept `reminder_minutes`; an explicitly supplied null clears the reminder, while omission preserves it. Reminders are owner-scoped `Note` todos with calendar label/source. Passed events skip creation, and a reminder whose intended time passed is clamped to now. Legacy matching uses generated title plus due time rather than an event UID; deleting reminders uses the title/source/owner match, so similarly named events remain a compatibility-sensitive boundary. `GET /api/calendar/events/{uid}` resolves recurring occurrence IDs back to the owner-visible base event.

`src/email_calendar_import.py` owns invitation revision state through `EmailCalendarInvitation`: identity hashes owner, normalized sender, ICS UID, and optional recurrence id instead of letting untrusted ICS UIDs address arbitrary local events. Sequence/DTSTAMP ordering suppresses stale replays, cancellation wins equal-version ties and leaves tombstones, and detached occurrences exclude their original series instance. Fixed striped file locks serialize imports across processes. Unsupported reply methods are ignored, and `THISANDFUTURE` revisions require a replacement series.

Task create/update persist sealed `request_authority_json`; execution binds that authority to LLM/research work rather than deriving permission from task output. Task endpoint resolution uses owner-visible registered endpoint bases or their exact derived chat URL before runtime credentials are attached; scheme, host, effective port and full trimmed path must match, with no userinfo, parameters, query or fragment. Legacy shared endpoint visibility is retained. The scheduler helper catches credential resolution exceptions and can continue with empty headers, so this is not a universal no-network-on-resolution-failure guarantee. Authority/effect contracts are owned by `src/agent_runtime`, not the scheduling layer.

## Scheduler Cache And Native Task Details

Scheduler `_cached` requests share one pending future per key with a TTL. Waiters shield the shared work from their own cancellation; completion/failure removes only the matching pending future, and failures can retry rather than being cached as success. Endpoint discovery separately caches successful empty Tailscale results, while discovery failures do not become successful empty cache entries.

Task/assistant endpoint updates accept registered owner-visible routes, canonicalize empty values to no override and reject invalid routes. Local shell/script/Cookbook scheduled actions require their sealed native backend capability; missing capabilities fail closed and raw external/SSH execution cannot borrow it. Headless task/background continuations close their streams in the originating task, preserve authority, honor replacement final responses and distinguish provider failure from successful completion.

`NotificationLog` GET is owner-scoped and non-consuming, defaults to 200 rows and clamps to 1000. Notification insert title/body limits are 200/2000 characters; notification text does not grant task authority. Calendar reminder matching is legacy title/source/owner-based rather than UID-linked: nearest eligible due time within zero to seven days of the base event start can match, while deletion removes all same-title matches rather than discriminating by exact alarm time. Negative offsets clamp to zero, passed events do not create reminders, passed alarm time clamps to now, explicit null clears and omission preserves.

## Notes Frontend State And Lifetimes

The canonical Notes composition entry owns one `createNotesState()` instance, injected HTTP/storage/notification ports, application workflows and UI factories. Domain modules own note rules and local-time recurrence. Application modules own query/order, optimistic card/checklist/deletion, selection, the note edit session (`noteSession.js`) and this tab's own writes (`noteVersions.js`), agent actions and reminders; UI modules delegate mutations and transport through those operations. The legacy facade preserves default/named open/close/toggle/new/openNote/badge methods and aliases, including named-only reminder-dot dismissal, without exposing mutable state.

Background startup is idempotent: after three seconds it loads active notes (unless the panel is already open on active notes: that list is the panel's, and swapping it without a redraw left stale cards and hid changes from the 20 s re-read), then starts a 30-second reminder interval and immediate check. Close/minimize/force-close dispose panel resources but leave that page-owned interval running. Scans use the current shared note collection, skip archived/date-only/fired notes, fire within the previous minute, and advance or mark older reminders; archived-only/error-cleared lists can still defer active reminders. Server synthesis has a 1.5-second local-notification fallback, with toast/highlight persistence. This browser path remains separate from backend delivery receipts.

The note window (`ui/noteWindow.js`) is the only editor, on desktop and phones. Clicking a card opens it; one is open at a time, opening another flushes the current one, it minimises to a `Note: <title>` dock chip, and the legacy facade's `openNote(id)` opens it from chat links. On phones it is a full-height sheet with 16 px text so iOS does not zoom on focus. The sheet has no close or minimise button there: a swipe down (the shared gesture in `static/js/ui.js`, which hides the modal and fires `modal-dismissed`) closes the window through `close()`, the path the close button and Escape take, so pending edits are flushed and the window's state is cleared; minimising is a desktop action. While the phone keyboard is up (`keyboard-open` on the root, with the visual viewport's pan in `--keyboard-viewport-top`) the sheet is placed and sized to the visible area, the window opts out of `ui.js`'s focus scroll (`data-keyboard-scroll="off"`) and scrolls its own text box to keep the caret between the title bar and the keyboard (`watchCaret`). Its controls and the share popover's have hit areas of at least 44 px on touch screens; the panel's search and quick-add inputs are 16 px on phones too. A card's title is a button (`role="button"`, `tabindex="0"`) that opens the note on Enter or Space. Closing the window, deleting the note or leaving it puts focus back on the element that opened it, or on the note's card. The in-grid form, the mobile fullscreen editor, the form draft autosave and the form checklist rows are gone, along with the Note/Todo/Draw switch and `#tag` typed into the title; the tag field still accepts `#tag`. The quick-add bar (`ui/quickAdd.js`) has one entry, a note, and no Note/To-do toggle: a click or the first keystroke opens a new note window with what was typed as its title, Enter in the title moves to the body, and a to-do list is made there with the toolbar's Checklist (`note_type` follows the content). Its photo button opens a new note on the image picker.

The open window has its own history entry (`ui/windowRoute.js`), `#note-<id>` (the id URL-encoded; only an id of 1 to 128 letters, digits, `_` or `-` is read back). Opening a note pushes the entry, so Back closes the window through the same path as the close button (pending edits saved) and puts back the chat hash it was opened over, and Forward opens it again if the note is still readable. Closing it by hand takes the entry back off with `history.back()`, but only an entry this page pushed: one from an earlier load or another site is left in place and only loses its hash. One note replacing another reuses the entry; a new note gets the entry at once and its hash when its first save gives it an id. A page loaded on `#note-<id>` opens that note over an entry without the hash, so Back from it stays in the app; a note that is gone or unreadable opens nothing and its hash goes. The entry keeps the chat it is open over in `history.state` (`odysseusChatId`, kept current by `static/js/sessions.js` while the note is open, so switching chats does not overwrite `#note-<id>`): a reload, which keeps `history.state`, comes back to that chat with the note on top, and a `#note-<id>` link in a new tab opens over the chat a plain load gives. A chat's note link no longer strips a `#note-` hash; the legacy `#open=notes&note=` hash is still cleared. Opening a note whose window is already open raises that window, or restores it from its dock chip, instead of reopening it.

The body (`ui/richBody.js`) shows the rendered note and is edited in place; Markdown source mode swaps it for a textarea with the raw content. Content is split into markdown blocks (`splitMarkdownBlocks()` in `domain/markdownSerializer.js`). A block that was not touched is written back byte for byte, so editing one paragraph never reformats the rest; an edited block is serialized from the DOM in the notes dialect, keeping code languages, tables, nested and numbered lists, blank lines and multi-line quotes, and escaping typed markdown characters. Nothing is locked: every part of a note is edited in place. The window renders with `sourceMap: true`, so a link carries its target as written (any scheme, a title), a fence its opener and closer, and a table its column alignment; what has no rich form (math, mermaid, `<details>`, SVG and other raw HTML) becomes an island (`.md-island`, `data-md-src`) that sits in the text like one character and, on click, opens a menu that edits its markdown in place or removes it. An edited block is written back through a line-then-character diff against what the serializer read when the block was rendered (`domain/sourceFidelity.js`): every character the edit kept keeps its stored bytes (escapes, spacing, `~~~`, delimiter rows) and typed text is written canonically; when the patched text would not render like the edit, the canonical text is saved. A block the editor still cannot write is kept as stored and the editor's reading of the edit goes to the session as `unsaved`: the rest of the note saves, the draft keeps the edit and is not cleared by a save, and the window shows "Part of this edit is not saved: the editor cannot write it. It is kept on this device." with a Markdown source button that opens the source with the typed text in it. The toolbar adds underline, highlight, superscript and subscript, written as `<u>`, `<mark>`, `<sup>` and `<sub>` (Cmd/Ctrl+U, Cmd/Ctrl+Shift+H). The link menu has a title field and keeps an untouched target as written. A markdown image the notes image policy will not load stays a link, never fetched; with the caret in it, the link button opens an Image link menu for its address and description. Copy and cut carry the selection as markdown, so a cut island or link pastes back as itself. The toolbar is one tab stop (`role="toolbar"`) moved through with the arrow keys, Home and End, and on phones it is one row that scrolls sideways, with the shared toolbar's edge fade; while the text or its source has focus the footer folds to no height, so Tab still reaches it once the text has lost focus. A focused image opens its size menu on Enter or Space, the arrow keys move through the menu, and closing it returns focus to the image. Escape closes the link menu back into the body, and Escape in the tag input closes its suggestions first, then the window, like the title and body. Each task's checkbox is named after the task's text (`aria-label`), kept up to date as the text is typed. Paste is plain text only, and the link menu accepts `http(s)`, `mailto:` and `tel:` targets, site paths and anchors, and puts `https://` in front of a bare domain; anything else is refused (`normaliseLinkUrl`).

`application/noteSession.js` owns saving. Nothing is written on open, blur or close unless the note was edited. An edit is backed up to localStorage and saved 600 ms later (`AUTOSAVE_DELAY_MS`) as the whole document (`replace_content: true`) with the `body_revision` the window last saw, and all writes of one session go through one queue. The first edit of a burst is backed up at once and the edits that follow within 300 ms (`DRAFT_BACKUP_INTERVAL_MS`) together, so a keystroke in a long note does not serialize the whole document; a save, a flush, closing the window and the page going away (`pagehide`, a hidden tab) write any pending backup. A new note is created by its first non-empty save, so an untouched new note creates nothing. A 409 keeps the local text in the draft, the session reads the current note, and the window shows "This note changed elsewhere." with Reload (adopt the server copy) or Keep mine (write the local text over it, against the new revision). A successful save clears only the draft it wrote. A draft records the `body_revision` it was typed against: the next time the note opens, a draft typed against the current revision is offered back with Restore / Discard, while one typed against an older revision, or left by another tab (kept in `odysseus-note-recovery-<id>`), is only offered to copy from, so it can never be written over a newer note. Checkbox flips go through the toggle route with the window's `body_revision` after pending text is saved, and a version this tab wrote itself (`noteVersions.js`, e.g. a card checkbox ticked behind the open window) is followed rather than reported as a conflict. Images and sketches are inserted inline (see "Note Images"); an existing drawing opens as a note with its image, and re-drawing it is not supported.

Sharing in the UI: when signed in, the owner gets a Share button with a count in the window header. Its popover (`ui/sharePopover.js`) has View / Edit for the accounts the note is shared with, each with a switch. For an admin (`directory: true`) it also lists every other account with a switch. For anyone else it has a username field and a Share button instead: Enter or Share sends the name, the account appears as View once the server finds it, and a name with no account shows "No account with that name." and shares nothing. Each change saves at once. Focus moves into the popover when it opens, Tab stays inside it, and closing it returns focus to Share. "Couldn't load users." (with retry), "No other users on this instance." (admin only) and "Your account is not allowed to share notes." (403) are separate states. Notes shared with the caller come after their own under a "Shared with me" header, with a filter chip of the same name; while that header is shown the grid packs cards in order (`grid-auto-flow: row`, not `dense`), so no shared card fills a gap above it; incoming cards show the owner's name and the caller's shared cards show `Shared · n`. A card shared with the caller has no pin, done, archive, delete, colour, select or drag; on a view-only card the add-item input is gone and tapping a task opens the note instead of ticking it. A view-only window shows "View only, shared by X", no toolbar, a read-only title and body, a disabled reminder button and only **Leave note** in the footer, and its session never saves or keeps a draft; paste and drop do nothing. An edit window edits content, title and tasks, and its footer also has only Leave note, in the place of the owner's Delete: it asks first, drops anything unsaved and closes the window. (The card's own menu, which also lists Leave note, sits in the card action row that the cards keep hidden.) Its Copy puts the title and the note's markdown on the clipboard (`_serializeNoteForCopy`), with the checklist once and its nesting kept. While the panel is open and the tab is visible, `GET /api/notes` is re-read every 20 s (`NOTES_REFRESH_MS`) with the last `ETag`, so an unchanged list costs a 304 and no redraw. The re-read is skipped while the note window's body has focus, the share or Ask popover is open, select mode is on, or an input in the panel is focused; a failed read keeps the current list, and `me` is refreshed on every poll so a renamed account keeps working. An open window follows the re-read: its tags and reminder are refreshed from the list's copy unless one of its own meta writes is in flight or the reminder menu is open, so a tag or reminder edit never writes back a stale list. A collaborator's window has no colour ring; the colour is the owner's. Select all picks only the caller's own notes, and a bulk archive or delete toast counts what the server accepted and says how many it refused.

Agent affordances (`ui/noteAgent.js`), all owner-only: an agent button on each open task row, injected after render with `contenteditable=false` and `data-md-skip` so the serializer and the editor's block snapshots ignore it, in the tab order, reading the row's text at click time and opening the Ask popover about that item, shown on hover in the window and on cards (on touch screens, dimmed at all times in the window and not shown on cards), hidden on done rows, in select mode and on notes shared with the caller, and added to a newly typed task after its save; the window footer's Ask popover; an "Agent chat" footer button once `agent_session_id` is set; and an "Agent" tag on the card. The toast after a start reads "Agent working in the background" with an Open chat action. Opening the agent chat closes the note window (which flushes it) and the panel, then loads and selects the session.

History (`ui/historyPanel.js`, `application/noteHistory.js`, `domain/historyText.js`), owner only, on saved notes: a History button in the window footer and "History (N)" in the meta line (`version_count`) open the list in place of the body, pending typing saved first. A "Now" row comes first, then the versions grouped by day with relative times and the exact time in a tooltip; an agent version links its chat unless the chat was deleted. A version is the note just before a change, and the list's `GET /api/notes/{id}/versions/{vid}` also carries `after`, the next newer version (the note itself for the newest). The chosen entry shows that change under "What this change did:": version to `after`, the same pair the one-line summary is read from, with the fields that differ and a line diff, removed lines struck through in `--red` and added lines on a `--fg` tint in bold. "Undo this change" restores the version; on an older entry the button reads "Undo this change and everything after it", and "Show what undoing does" opens a second diff, the note as it is now to the version. A restore puts the stored bytes back, and the toast "Restored the version from <time>" has an Undo that restores `undo_version_id`. "See what changed", in the "Agent edited this note" toast and on a `manage_notes` update or toggle_item row in the chat, opens the History on that chat's latest agent edit.

Context cards (`ui/contextStrip.js`, `domain/contextNotes.js`): nothing shows when the chat carries no note. The notes selected for the chat (Select, then Send to Agent) are small cards above the composer, each with an x that takes it out of the selection; the note a chat was started from (the sessions list's `note_scope_id`) is a card at the top of the conversation, with no x. A sent user message stores the notes its turn carried as `metadata.context_notes` (id, title as sent, and the focus todo on a note-started run) and shows them as attachment cards (`buildContextNoteCards` in `static/js/chatRenderer.js`) that survive a reload. A card opens its note in the note window over the chat. Cards reuse `.note-card` and the colour classes, carry `data-context-note-id` rather than `data-note-id`, and show the title and three lines or a checklist's first open items; on a phone they are one row that scrolls sideways.

A 404 on a save or a checkbox flip means the note was deleted, its owner's account was removed, or it is no longer shared with the caller. The session marks itself gone: it stops writing, drops that note's draft and removes the card, and the window shows "This note no longer exists or is no longer shared with you. Changes here are not saved." with Close. The text stays in the window so it can be copied.

Selection dispatches `odysseus:notes-context-selected` synchronously and exits only when the consumer sets `accepted`; chat retains context/session authority. Closing releases owned portals/listeners/gestures/observers, and late fetch/masonry work checks panel connectivity/open state. It does not add universal async generation guards: fetch remains last-completion-wins.

## Current Gaps

- `do_manage_notes()` should match HTTP note-route owner behavior for legacy null-owner notes.
- Auth-disabled agent tools can produce or read broader owner scopes than route handlers because they receive `owner=None`; tasks, notes, and calendar need aligned policy/tests.
- Task webhook tests should keep exercising live route token behavior and
  admin-only action blocking, not only middleware/source strings.
- Reminder delivery needs tests across frontend `/fire-reminder`, backend `dispatch_reminder()`, scheduler note pings, channel degradation, and dedupe.
- Codex calendar scope and owner mapping needs dedicated regression coverage; the todo bridge's scope gate is covered by `tests/test_codex_todo_scope_gate.py`.
- Direct DB CLIs need either documented route-bypassing support status or shared helpers to avoid owner/timezone/writeback drift.
- `scripts/odysseus-webhook` builds the live `/api/tasks/{task_id}/webhook/{token}` path with percent-encoded path segments; its direct DB token rotation/revocation behavior remains a local compatibility surface.
- Assistant default documentation/code comments still mention check-ins that are no longer auto-seeded.
- App backup import/export does not cover the calendar/task/note rows described by this spec.
- The legacy `Note.items` and `Note.image_url` columns stay in the schema: the rollback restores into them and readers still fold an unmigrated row's `items`. Dropping them needs its own migration once rollback is no longer wanted.
- `goal` and `draw` are stored editing modes, not derived from content, so a drawing note keeps `note_type = "draw"` even when its content is ordinary markdown.
- An existing drawing cannot be re-edited on its canvas: it opens in the note window as a note with its image.
