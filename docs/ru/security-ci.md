# Руководство по безопасности CI

Этот проект выполняет набор автоматических проверок безопасности при pull request и определённых пуших в ветки. Эта страница объясняет, что делает каждая проверка, может ли она заблокировать слияние, и какие разовые настройки следует включить для получения максимальной выгоды.

## Что запускается и зачем

Большинство проверок находятся в файлах под `.github/workflows/`. CodeQL настроен через стандартную настройку сканирования кода GitHub, поэтому он отображается как динамический workflow GitHub, а не как файл workflow, добавленный в репозиторий. Они запускаются автоматически; вы не запускаете их вручную.

| Проверка | Защита от | Блокирует слияние? |
|---|---|---|
| **Сканирование секретов** (gitleaks) | Случайное или намеренное добавление API-ключа, токена или пароля в коммит | Да |
| **Безопасность workflow** (actionlint + zizmor) | Сломанный или небезопасный файл автоматизации, который может утечь токен доступа к репозиторию | Да |
| **Проверка зависимостей** | Pull request, добавляющий библиотеку с известной уязвимостью | Да |
| **pip-audit** | Известные уязвимости в уже используемых Python-библиотеках | Нет (рекомендация) |
| **Сканирование контейнера: hadolint** | Ошибки и небезопасные паттерны в `Dockerfile` | Да |
| **Сканирование контейнера: Trivy** | Известные уязвимости в Docker-образе | Нет (рекомендация) |
| **CodeQL** | Реальные баги в собственном коде приложения: инъекции, ошибки аутентификации, обход путей | Нет (рекомендация) |

«Блокирует слияние» означает, что на pull request появляется красный крестик, и, после включения настройки ниже, кнопка **Merge** отключается, пока проблема не будет исправлена.

«Рекомендация» означает, что результаты отправляются во вкладку **Security** репозитория, чтобы вы могли просмотреть их в удобное время, но слияние никогда не блокируется. Это намеренно рекомендательный характер: они часто помечают давние проблемы в библиотеках других людей, а не то, что внесено данным pull request.

## Где появляются результаты

- **Вкладка Checks pull request**: результат прохождения каждой проверки. Зелёная галочка — хорошо; красный крестик требует внимания.
- **Вкладка Security репозитория**: подробные результаты от рекомендательных сканеров (Trivy и CodeQL). Это ваша панель мониторинга.

## Если проверка не прошла

- **Сканирование секретов не прошло**: возможно, был закоммичен реальный учётный документ. Отнеситесь к этому как к утечке: ротируйте (перегенерируйте) этот ключ или токен немедленно, затем удалите его из файла. Не просто удаляйте коммит; считайте, что его уже видели.
- **Проверка зависимостей не прошла**: pull request добавляет библиотеку с известной уязвимостью. Попросите автора использовать исправленную версию или отклоните изменение.
- **hadolint / безопасность workflow не прошли**: автор изменил `Dockerfile` или файл автоматизации способом, который линтер отклоняет. Попросите его исправить сообщение, показанное в неработающей проверке.

## Разовые настройки для включения

Эти две настройки раскрывают полную ценность. Вы делаете их только один раз.

### 1. Требуйте блокирующие проверки перед слиянием

Это заставит кнопку **Merge** отказываться работать, пока проверки не пройдут.

1. Перейдите к репозиторию на GitHub.
2. Нажмите **Settings** (справа вверху репозитория).
3. В левой боковой панели нажмите **Branches**.
4. В разделе **Branch protection rules** нажмите **Add branch ruleset** (или **Add rule**) и установите шаблон имени ветки на `dev` (это ветка, на которую нацелены все pull request; `main` перемещается вперёд при релизах).
5. Включите **Require status checks to pass before merging**.
6. В появившейся строке поиска добавьте эти проверки по имени:
   - `Python syntax (compileall)`
   - `JS syntax (node --check)`
   - `gitleaks`
   - `actionlint`
   - `zizmor (Actions SAST)`
   - `hadolint (Dockerfile lint)`
   - `dependency-review (PR gate)`

   Первые две来源于 проверки корректности (`ci.yml`); остальные — из этого набора безопасности. Оставьте pytest, pip-audit, Trivy и CodeQL отмеченными как рекомендательные.
7. Также включите **Require a pull request before merging** и **Require review from Code Owners** (это использует файл `.github/CODEOWNERS`, поэтому каждое изменение требует вашего одобрения).
8. Нажмите **Create** / **Save changes**.

Примечание: имя проверки появляется в списке только после того, как она была запущена хотя бы один раз, поэтому дайте workflow'ам выполниться на одном pull request, а затем добавьте их сюда.

### 2. Включите функции вкладки Security

1. **Settings -> Code security** (или **Code security and analysis**).
2. Включите **Dependency graph** (обычно включен по умолчанию для публичных репозиториев) — это обеспечивает Dependency review и Dependabot.
3. Включите **Dependabot alerts** и **Dependabot security updates**.
4. В разделе **Code scanning** используйте **Set up -> Default** для CodeQL. Затем GitHub запускает CodeQL как динамический workflow без ограничений fork-токена, которые влияют на добавленные в репозиторий расширенные workflow'ы.

   Не добавляйте добавленный в репозиторий CodeQL workflow, пока включена настройка по умолчанию: GitHub отклоняет расширенную загрузку CodeQL, когда активна настройка по умолчанию. Если проекту позже потребуется расширенный CodeQL workflow, сначала отключите настройку по умолчанию и оставьте только один путь публикации CodeQL.

## Поддержание актуальности

`.github/dependabot.yml` открывает небольшие еженедельные pull request для обновления пакетов Python и npm, базового образа Docker и закреплённых действий автоматизации. Просматривайте и сливайте их как любой другой pull request; они поддерживают проект исправленным без ручного отслеживания.
