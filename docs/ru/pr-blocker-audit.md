# Аудит блокеров PR

`scripts/pr_blocker_audit.py` — это небольшой вспомогательный инструмент сортировки только для чтения для мейнтейнеров, которым нужно проверить пересечение открытых pull request перед.review или началом связанной работы.

Это инструмент сортировки, а не замена суждения мейнтейнера.

## Что он делает

- Читает метаданные открытых PR из локального JSON-файла или из `gh`.
- Сообщает о файлах, затронутых более чем одним открытым PR.
- Группирует активную работу по широким областям кода.
- Ранжирует PR с помощью детерминированной эвристической оценки.
- Помечает возможных кандидатов на дубликаты на основе пересечения ключевых слов в заголовках и схожести изменённых файлов.
- Предлагает более спокойные области для консервативной новой работы.
- По умолчанию выводит Markdown, компактный терминальный вывод по запросу или машиночитаемый JSON.

## Что он не делает

- Не публикует комментарии.
- Не проверяет, не одобряет, не помечает, не закрывает, не сливает и не иным образом изменяет PR.
- Не добавляет и не запускает GitHub Actions.
- Не импортирует пакет приложения Odysseus.
- Не утверждает, что PR определённо заблокирован или дублируется.

## Гарантия безопасности только для чтения

Онлайн-режим только читает локальный JSON-файл. Режим реального времени выполняет команды GitHub CLI только для чтения:

```bash
gh pr list --repo OWNER/REPO --state open --limit 1000 --json number,title,author,files,mergeStateStatus,reviewDecision,updatedAt,url
```

Если у PR из этого списка отсутствуют или пусты метаданные изменённых файлов, режим реального времени заполняет их REST-вызовами только для чтения для каждого PR:

```bash
gh api --paginate "repos/OWNER/REPO/pulls/NUMBER/files?per_page=100"
```

Если эта команда на основе GraphQL не удаётся, используется запасной вариант:

```bash
gh api --paginate "repos/OWNER/REPO/pulls?state=open&per_page=100"
```

Получение файлов для каждого PR делает результаты пересечения в реальном времени полезными, но это может быть медленнее на репозиториях со сотнями открытых PR.

## Генерация входного JSON

Для повторяемых офлайн-аудитов сначала захватите метаданные PR:

```bash
gh pr list --repo OWNER/REPO --state open --limit 1000 --json number,title,author,files,mergeStateStatus,reviewDecision,updatedAt,url > open-prs.json
```

## Запуск офлайн-режима

```bash
python3 scripts/pr_blocker_audit.py --input open-prs.json
```

## Запуск режима реального времени

```bash
python3 scripts/pr_blocker_audit.py --repo OWNER/REPO
```

Режим реального времени получает до 1000 открытых PR по умолчанию. Используйте `--limit` для ограничения количества получаемых и анализируемых открытых PR и `--top` для ограничения количества отображаемых строк в ранжированных разделах:

```bash
python3 scripts/pr_blocker_audit.py --repo OWNER/REPO --limit 50 --top 10
```

Режим реального времени может занять время на больших очередях PR, поскольку он получает метаданные изменённых файлов для каждого PR, который не включил их в начальный ответ. Прогресс по умолчанию отображается в `stderr` только когда `stderr` является TTY:

```bash
python3 scripts/pr_blocker_audit.py --repo OWNER/REPO --progress auto
python3 scripts/pr_blocker_audit.py --repo OWNER/REPO --progress always
python3 scripts/pr_blocker_audit.py --repo OWNER/REPO --progress never
```

Используйте `--quiet` для подавления прогресса и нефатальных предупреждений. Прогресс и предупреждения никогда не попадают в `stdout`, поэтому перенаправленные отчёты и файлы `--output` остаются чистыми.

Для более быстрого сканирования только метаданных полностью пропустите метаданные изменённых файлов:

```bash
python3 scripts/pr_blocker_audit.py --repo OWNER/REPO --no-fetch-files
```

## JSON-вывод

Используйте `--format json` для машиночитаемого вывода, пригодного для скриптов или инструментов обработки:

```bash
python3 scripts/pr_blocker_audit.py --input open-prs.json --format json
python3 scripts/pr_blocker_audit.py --input open-prs.json --format json --output report.json
```

JSON-вывод стабилен и детерминирован для одинакового входа. Используется `sort_keys=True`, поэтому порядок полей не изменяется между запусками. Он никогда не включает коды ANSI, даже с `--color always`. Текст прогресса всегда только в `stderr` и никогда не появляется в JSON-выводе.

Верхний объект содержит следующие ключи:

- `summary` — скалярная сводка: `total_prs_analyzed`, `unique_files_touched`, `prs_missing_changed_file_metadata`, `main_overlap_drivers`, `highest_risk_areas`, `recommended_first_review_target`
- `locked_areas` — список объектов с `area`, `files` (верхние пути строкой), `prs` (список номеров PR), `why`, `priority`
- `hot_files` — список объектов с `file`, `pr_count`, `pr_numbers` (список номеров PR); ограничено `--top`
- `review_priorities` — ранжированный список с `rank`, `number`, `score`, `title`, `url`, `merge_state`, `review_decision`, `reasons` (список); ограничено `--top`
- `duplicate_candidates` — список объектов с `pr_numbers` (список) и `titles` (список, по одному элементу на PR в группе)
- `safer_areas` — список строк

## Запись вывода в файл

```bash
python3 scripts/pr_blocker_audit.py --input open-prs.json --output pr-blocker-report.md
python3 scripts/pr_blocker_audit.py --input open-prs.json --format json --output report.json
```

Вывод в Markdown и JSON никогда не включает коды цвета ANSI. Коды ANSI удаляются защитно при записи любого выходного файла.

## Терминальный вывод и цвет

Используйте терминальный вывод для быстрых интерактивных сканирований:

```bash
python3 scripts/pr_blocker_audit.py --input open-prs.json --format terminal
```

Терминальный вывод включает заблокированные области, горячие файлы, приоритеты проверки/блокеров, возможных кандидатов на дубликаты и более безопасные области.

Цвет предназначен только для удобства чтения. Он никогда не включается в отчёты Markdown и удаляется защитно при записи выходных файлов. Режимы цвета:

```bash
python3 scripts/pr_blocker_audit.py --input open-prs.json --format terminal --color auto
python3 scripts/pr_blocker_audit.py --input open-prs.json --format terminal --color always
python3 scripts/pr_blocker_audit.py --input open-prs.json --format terminal --color never
```

`--no-color` сохраняется как псевдоним для `--color never`. С `--color auto` цвет используется только для терминального вывода на TTY, когда `NO_COLOR` не установлен и вывод не записывается в файл.

## Интерпретация заблокированных областей

Заблокированные области — это широкие категории с одним или несколькими открытыми PR. Область имеет более высокий приоритет, когда несколько PR её затрагивают, когда PR разделяют файлы или когда PR с наивысшей оценкой в этой области имеет сигналы риска. Отнеситесь к этому как к призыву проверить PR вместе.

`PRs missing changed-file metadata` подсчитывает PR, у которых всё ещё нет путей к изменённым файлам после получения файлов в реальном времени, или PR из офлайн-входных данных, которые не включали файлы. Эти PR всё ещё могут появляться в сводках областей по匹配 заголовков, но анализ пересечения файлов для них слабее.

`Docs / tooling / tests` — консервативный: PR с runtime не классифицируются там только потому, что они включают тесты или изменения README. Только документы, только README, только скрипты, только тесты или работа с ярлыком docs/tooling/test по-прежнему туда попадает.

`Other / unclassified` остаётся видимым для PR, которые не соответствуют правилам областей. Когда большая его часть связана с отсутствующими метаданными файлов, отчёт резюмирует это, не позволяя длинным спискам PR доминировать в разделе заблокированных областей.

## Интерпретация кандидатов на дубликаты

Кандидаты на дубликаты помечены как возможный дубликат / требует проверки человеком. Скрипт группирует PR только когда их наборы файлов сильно похожи и их заголовки разделяют значимые ключевые слова. Похожие PR всё ещё могут быть взаимодополняющими.

## Интерпретация эвристических оценок

Оценка приоритета проверки детерминирована для одинакового входа. Новизна измеряется относительно самой новой парсимой временной метки обновления PR во входных данных, и оценка использует простые веса для:

- прямых сигналов жизненного цикла авторизации, bearer-токена, API-токена, привилегий или разрешений
- ключевых слов безопасности, секретов или утечки данных
- ключевых слов персистентности, миграции, базы данных, SQLite или Postgres
- ключевых слов память, вектор, RAG, эмбеддинг или извлечение
- пересечения изменённых файлов
- чистого состояния слияния как небольшого сигнала применимости
- состояния проверки
- недавно обновлённых PR при наличии данных о временных метках

Более высокие оценки означают «проверить раньше», а не «правильно» или «готово к слиянию». Широкие PR могут получить высокую оценку, потому что они пересекаются со множеством файлов и могут блокировать другую работу, но они всё ещё требуют обычной проверки и валидации.

Грязное, заблокированное, конфликтующее и неизвестное состояние слияния отображаются как причины риска/осторожности. Они не добавляют сами по себе баллы важности.

## Примечание по дизайну: намеренная односкриптовая компоновка

`pr_blocker_audit.py` намеренно остаётся одним автономным скриптом. Цель — поддерживать этот вспомогательный инструмент для мейнтейнеров/контрибьюторов с минимальным трением, пока соглашения по инструментам репозитория и тестовым наборам всё ещё развиваются. Разделение на пакеты или модули не исключается, но откладывается до тех пор, пока не появится более чёткая устоявшаяся схема для следования.

## Ограничения

- Некоторые PR всё ещё могут не иметь изменённых файлов, если вызовы метаданных файлов GitHub завершаются неудачей или используется режим только метаданных.
- Классификация областей намеренно мала и редактируема.
- Сопоставление ключевых слов заголовков пропускает семантические дубликаты.
- Эвристическая оценка не может знать стратегию проекта, доступность рецензентов или скрытые цепочки зависимостей.
- Пустые или отсутствующие метаданные файлов создают валидный отчёт, но слабый анализ пересечения.
