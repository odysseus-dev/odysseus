# Резервное копирование и восстановление

Odysseus хранит всё ваше состояние в каталоге `data/` — базу данных SQLite (`app.db`), ключ шифрования Fernet (`data/.app_key`), хранилище, память, индексы RAG, личные документы и загрузки. Инструмент `scripts/odysseus-backup` делает снимок этого каталога в виде одного gzip-архива и восстанавливает его при необходимости.

Снимки безопасно делать во время работы приложения: базы данных SQLite копируются через собственный API `.backup` SQLite, а не через обычное копирование файлов, поэтому незавершённая запись не может повредить снимок.

> **Снимок содержит ваши секреты.** Архив включает ключ шифрования Fernet (`data/.app_key`), хранилище, сессии и все сохранённые токены провайдеров/API — поэтому относитесь к нему как к паролю. Храните резервные копии в приватном месте, никогда не коммитьте их в Git и предпочитайте зашифрованное место назначения при копировании за пределы сайта.

## Быстрый старт

Запустите инструмент из корня репозитория:

```bash
# Создать снимок → backups/odysseus-backup-<YYYYMMDD-HHMMSS>.tar.gz
./scripts/odysseus-backup snapshot

# Вывести список существующих снимков (новые первыми)
./scripts/odysseus-backup list

# Проверить целостность архива без его извлечения
./scripts/odysseus-backup verify backups/odysseus-backup-20260101-120000.tar.gz

# Восстановить (деструктивно — см. предупреждение ниже)
./scripts/odysseus-backup restore backups/odysseus-backup-20260101-120000.tar.gz --yes
```

Скрипт зависит только от стандартной библиотеки Python, поэтому любой `python3` из вашего `PATH` его запустит — не нужен активный виртуальный环境 приложения.

Каждая команда выводит JSON-результат. Добавьте `--pretty` для форматированного вывода.

## Команды

### `snapshot`

Записывает `tar.gz` из `data/` в `backups/<timestamp>.tar.gz`.

| Флаг | Эффект |
| --- | --- |
| `--out PATH` | Записать по указанному пути вместо места по умолчанию `backups/`. Должен быть **вне** `data/`. |
| `--include-research` | Включить `data/deep_research/` (по умолчанию пропускается — запуски исследований большие). |
| `--include-attachments` | Включить `data/mail-attachments/` (по умолчанию пропускается — кэшированные извлечения IMAP, воспроизводимые). |

По умолчанию снимок включает всё под `data/`, **за исключением** `deep_research/` и `mail-attachments/`. Личные загрузки и документы включаются.

```bash
# Снимок напрямую по пути смонтированного NAS
./scripts/odysseus-backup snapshot --out /mnt/nas/odysseus-$(date +%F).tar.gz

# Полный снимок, включая запуски исследований и вложения почты
./scripts/odysseus-backup snapshot --include-research --include-attachments
```

### `list`

Выводит список архивов в `backups/`, новые первыми, с размером и временем изменения.

### `verify PATH`

Открывает архив в режиме только для чтения и проходит по каждому элементу, чтобы убедиться, что он цел и безопасен для восстановления. Ничего не извлекается. Используйте это перед использованием старой резервной копии или после копирования между машинами.

### `restore PATH --yes`

Перезаписывает `data/` из архива.

> **Восстановление деструктивно.** Оно заменяет текущий каталог `data/`. `--yes` требуется, чтобы опечатанная команда не удалила ваше рабочее состояние.

Восстановление не является слепым удалением: перед извлечением инструмент **переименовывает ваш текущий `data/` в `data.before-restore-<timestamp>`** в корне репозитория. Если восстановление окажется неправильным, ваше предыдущее состояние всё ещё на месте — удалите восстановленный `data/` и переименуйте сохранённый каталог обратно. Путь восстановления также проверяется поэлементно: архивы, содержащие абсолютные пути, сегменты `..`, символические ссылки или что-либо за пределами `data/`, отклоняются.

## Планирование удалённых резервных копий

Выходные данные архива хорошо сочетаются с cron и любым инструментом копирования. Например, ежедневный снимок, копируемый на удалённое хранилище:

```cron
0 3 * * *  cd /path/to/odysseus && ./scripts/odysseus-backup snapshot --out "/mnt/nas/odysseus-$(date +\%F).tar.gz"
```

Замените целевой путь `--out` на `scp`, `rclone`, `s3cmd` или аналогичный для отправки снимка в удалённое хранилище.

## Docker vs нативные установки

Инструмент читает `data/` и записывает `backups/` относительно корня репозитория, поэтому важен угол запуска:

- **Нативные установки** — запускайте из корня репозитория, как показано выше. `data/` и `backups/` находятся в каталоге репозитория.
- **Docker** — `docker-compose.yml` монтирует `./data` хоста в `/app/data`, поэтому рабочие данные также присутствуют на хосте. **Запускайте инструмент на хосте** из корня репозитория; снимок читает смонтированный `./data` и записывает в `./backups` на хосте. Запуск *внутри* контейнера не рекомендуется, поскольку `backups/` не является смонтированным томом, и архив будет потерян при пересоздании контейнера.

> **Оговорка по ChromaDB (только Docker).** В настройке Docker ChromaDB хранит свои векторы в отдельном томе, управляемом Compose (объявленном как `chromadb-data`), а **не** под `./data`. Поэтому `odysseus-backup` не захватывает хранилище ChromaDB Docker. Сделайте его резервную копию отдельно, если он вам нужен. Compose добавляет префикс к тому с именем проекта, поэтому сначала найдите реальное имя (`docker volume ls | grep chromadb`), затем заархивируйте его — например:
>
> ```bash
> docker run --rm -v <project>_chromadb-data:/data -v "$PWD":/backup \
>   alpine tar czf /backup/chromadb.tar.gz -C /data .
> ```
>
> При нативных установках ChromaDB находится в `data/chroma/` и включается в снимок в обычном порядке.
