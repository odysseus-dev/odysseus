# Руководство по настройке Odysseus

Эта страница содержит подробные инструкции по установке, развёртыванию, устранению неполадок и конфигурации, чтобы не загромождать основной README.

## Быстрый старт

> **Примечание о ветках:** `dev` — ветка по умолчанию, содержащая последние изменения разработки, но она может быть нестабильной. Для более стабильной проверенной ветки используйте [`main`](https://github.com/pewdiepie-archdaemon/odysseus/tree/main).

Настройки по умолчанию работают из коробки: клонируйте, запустите, затем настройте модели/поиск/электронную почту в разделе **Настройки**. Редактируйте `.env` только для переопределения уровней развёртывания, таких как `APP_BIND`, `APP_PORT`, `AUTH_ENABLED`, `DATABASE_URL` или предустановленный пароль администратора.

При первичной настройке Odysseus создаёт учётную запись администратора (`admin`, если `ODYSSEUS_ADMIN_USER` не установлен) и выводит временный пароль в терминал. При установке через Docker ту же строку можно найти в `docker compose logs odysseus`. Используйте этот пароль для первого входа, затем измените его в разделе **Настройки**.

Хотите внести вклад? См. [CONTRIBUTING.md](../CONTRIBUTING.md) для инструкций по настройке, тестированию и отправке pull request.

### Docker (рекомендуется)
```bash
git clone https://github.com/pewdiepie-archdaemon/odysseus.git
cd odysseus
cp .env.example .env       # необязательно, но рекомендуется для явных значений по умолчанию
docker compose up -d --build
```
Для включения необязательных компонентов в образе (просмотр PDF, извлечение Office; включает AGPL PyMuPDF) соберите с помощью `docker compose build --build-arg INSTALL_OPTIONAL=true` перед `up`.

Откройте `http://localhost:7000`, когда контейнеры будут готовы. Docker Compose по умолчанию привязывает веб-интерфейс к `127.0.0.1`. Если порт занят, установите `APP_PORT=7001` в `.env` и пересоздайте контейнер. Устанавливайте `APP_BIND=0.0.0.0` только когда вам намеренно нужен доступ по локальной сети/обратному прокси.

> **На Mac с Apple Silicon (серия M):** Docker не может использовать GPU Metal, поэтому Cookbook served локальные модели только на CPU. Для ускоренной на моделях работы с GPU запускайте нативно — см. [Apple Silicon](#apple-silicon) ниже.

### Нативная установка Linux / macOS
```bash
git clone https://github.com/pewdiepie-archdaemon/odysseus.git
cd odysseus
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python setup.py
python -m uvicorn app:app --host 127.0.0.1 --port 7000
```
Требования: Python 3.11+. Cookbook также требует `tmux` для фоновых загрузок и запуска моделей. Само приложение легковесное; локальное обслуживание моделей — ресурсоёмкая часть, зависящая от модели, среды выполнения, GPU и VRAM, поэтому небольшие хосты могут подключаться к API или удалённым серверам моделей. Используйте `--host 0.0.0.0` только когда вам намеренно нужен доступ по локальной сети/обратному прокси.

### Apple Silicon
Docker на macOS не может использовать GPU Metal. Для ускоренной на GPU работы Cookbook на Mac серии M запускайте Odysseus нативно:

```bash
git clone https://github.com/pewdiepie-archdaemon/odysseus.git
cd odysseus
./start-macos.sh
```

Приложение запускается на `http://127.0.0.1:7860`. Для доступа с телефона по доверенной локальной сети/VPN, например Tailscale, привяжите все интерфейсы:

```bash
ODYSSEUS_HOST=0.0.0.0 ./start-macos.sh
# затем откройте http://<tailscale-ip>:7860
```

Скрипт также читает `.env` при запуске, поэтому `APP_BIND=0.0.0.0` и `APP_PORT`, установленные там, применяются автоматически без переопределения через командную строку.

Поддерживайте `AUTH_ENABLED=true` (значение по умолчанию) перед привязкой вне loopback. Не под exposes этот порт напрямую в публичный интернет. Для сборки кликабельной обёртки приложения:

```bash
./build-macos-app.sh
```

<summary>Cookbook, GPU, Ollama и устранение неполадок</summary>

**Встроенные сервисы Docker.** Compose запускает Odysseus, ChromaDB, SearXNG и ntfy. Odysseus и порты встроенных сервисов по умолчанию привязаны к `127.0.0.1`, поэтому они доступны с хоста, но не暴露ены в локальную сеть/публичный интернет, если вы явно не включите это.

**Хранилище Cookbook в Docker.** Загрузки находятся в `./data/huggingface` (`~/.cache/huggingface` в контейнере). Python CLI и движки serve, установленные через Cookbook, находятся в `./data/local` (`~/.local` в контейнере), поэтому они сохраняются при пересоздании контейнера.

**Удалённые серверы.** В **Cookbook -> Settings -> Servers** сгенерируйте SSH-ключ Odysseus и добавьте публичный ключ в `~/.ssh/authorized_keys` удалённого сервера. С хоста также можно запустить:

```bash
ssh-copy-id -i data/ssh/id_ed25519.pub user@server
```

**Доступ к Docker на хосте (явное включение).** Docker Compose по умолчанию намеренно не монтирует `/var/run/docker.sock`. Вы всё равно можете подключить Odysseus к существующим Ollama, vLLM и другим совместимым с OpenAI endpoint'ам без доступа к Docker socket.

Управление Cookbook/локальным Docker-демоном требует явного включения через overlay ниже. Прямой доступ к Docker socket — это доверенная операция, поскольку он фактически предоставляет широкий контроль над Docker-демоном хоста. Рабочие процессы Docker для удалённых серверов через SSH остаются предпочтительными.

Добавьте эти значения в `.env` или экспортируйте их в shell перед запуском `docker compose`:

```bash
COMPOSE_FILE=docker-compose.yml:docker/host-docker.yml
DOCKER_GID=<host docker group gid>
```

Сочетайте доступ к Docker на хосте с GPU overlay, когда оба намеренно необходимы:

```bash
COMPOSE_FILE=docker-compose.yml:docker/gpu.nvidia.yml:docker/host-docker.yml
# или
COMPOSE_FILE=docker-compose.yml:docker/gpu.amd.yml:docker/host-docker.yml
```

**GPU overlay для Docker.** Пользователи только с CPU могут пропустить этот раздел. Cookbook может обнаружить только те GPU, которые Docker предоставляет контейнеру — если среда выполнения хоста или проброс устройства не настроены, Cookbook увидит встроенный GPU, другую карту или CPU вместо вашего целевого GPU.

Для NVIDIA `scripts/check-docker-gpu.sh` диагностирует проброс GPU и может опционально установить среду выполнения хоста или обновить `.env`.

```bash
# Только диагностический режим (по умолчанию — ничего не устанавливает, никогда не редактирует .env):
scripts/check-docker-gpu.sh

# Вывести команды установки для конкретной ОС без их запуска:
scripts/check-docker-gpu.sh --print-install-commands

# Установить NVIDIA Container Toolkit на Ubuntu/Debian (требует sudo):
scripts/check-docker-gpu.sh --install-nvidia-toolkit

# Записать COMPOSE_FILE в .env (только когда проброс GPU подтверждён как рабочий):
scripts/check-docker-gpu.sh --enable-nvidia-overlay

# Полная настраиваемая установка — установить toolkit, затем включить overlay, если проброс работает:
scripts/check-docker-gpu.sh --install-nvidia-toolkit --enable-nvidia-overlay
```

Примечания по безопасности:
- Приложение никогда не устанавливает среду выполнения GPU хоста автоматически.
- Приложение никогда не редактирует `.env` автоматически.
- `.env` изменяется только при явной передаче `--enable-nvidia-overlay` и только после успешного проброса GPU. `--yes` пропускает запросы, но не обходит проверку проброса.
- Резервные копии `.env.bak.*`, созданные `--enable-nvidia-overlay`, игнорируются Git и контекстом сборки Docker.

Для ручного включения без скрипта добавьте это в `.env`:

```bash
COMPOSE_FILE=docker-compose.yml:docker/gpu.nvidia.yml
```

**AMD / ROCm.** Настройка AMD — это только диагностический режим плюс ручное редактирование `.env`. Запустите:

```bash
scripts/check-docker-amd-gpu.sh
```

Затем добавьте указанные значения в `.env`, заменив `RENDER_GID` на числовую группу render вашего хоста:

```bash
COMPOSE_FILE=docker-compose.yml:docker/gpu.amd.yml
RENDER_GID=989
```

Для поддержки GPU NVIDIA/AMD также прочитайте комментарии в выбранном файле overlay: docker/gpu.nvidia.yml или docker/gpu.amd.yml.

**Интерфейсы управления стеком (Portainer, Coolify, Dockhand и т.д.).** Эти инструменты часто принимают только один файл Compose и не всегда корректно обрабатывают `COMPOSE_FILE` или несколько overlay через `-f`. Пользователи CLI должны продолжать использовать рабочий процесс overlay через `COMPOSE_FILE` выше. Для интерфейсов управления стеками направьте стек на один из автономных файлов, которые объединяют базовый стек с настройками GPU:

- `docker-compose.gpu-nvidia.yml` — по-прежнему требует NVIDIA Container Toolkit на хосте.
- `docker-compose.gpu-amd.yml` — по-прежнему требует настройки ROCm/kfd/DRI на хосте, членства в группе `video`/`render` и `RENDER_GID` при необходимости.

Базовый `docker-compose.yml` и overlay `docker/gpu.*.yml` остаются основным источником; автономные файлы отражают их для однофайловых развёртываний.

Проверьте после включения любого overlay:

```bash
docker compose exec odysseus nvidia-smi -L   # NVIDIA
docker compose exec odysseus sh -lc 'test -e /dev/kfd && test -d /dev/dri && ls -l /dev/kfd /dev/dri/renderD*'  # AMD
```

> **Проброс GPU ≠ CUDA для llama.cpp.** Успешный `nvidia-smi` внутри контейнера подтверждает доступ к GPU Docker, но llama.cpp также требует `cudart` и CUDA Toolkit во время выполнения. Если в логах Cookbook отображается `Unable to find cudart library`, `Could NOT find CUDAToolkit`, `CUDA Toolkit not found` или тензоры/слои назначены на CPU — это проблема сборки Cookbook/llama.cpp, а не сбой проброса Docker. Переустановите движок serve через **Cookbook → Dependencies** для получения сборки с поддержкой CUDA.
>
> Та же проблема применима к AMD/ROCm: наличие `/dev/kfd` и `/dev/dri` внутри контейнера подтверждает проброс устройств, а не пользовательское пространство ROCm или сборку vLLM/llama.cpp с поддержкой ROCm. `rocm-smi` и `rocminfo` не ожидаются в минимальном образе Odysseus.

**Ollama с Docker.** Если Ollama работает на хосте, добавьте этот endpoint в настройки:

```text
http://host.docker.internal:11434/v1
```

Ollama должен слушать вне собственного интерфейса loopback:

```bash
OLLAMA_HOST=0.0.0.0:11434 ollama serve
```

Это подключает Odysseus в Docker к серверу Ollama, который уже работает на вашем хост-машине; оно не запускает Ollama внутри контейнера. `host.docker.internal` — имя хоста Docker для хост-машины внутри контейнера. Cookbook **Serve** — это отдельный рабочий процесс для раздачи скачанных моделей через Odysseus/llama.cpp, поэтому пользователям Windows с уже установленным Ollama обычно достаточно добавить endpoint в настройках.

**Полезные проверки.**

```bash
docker compose ps
docker compose logs --tail=120 odysseus
docker compose logs odysseus | grep -E 'ChromaDB|MemoryVectorStore|DEGRADED'
```

**Подробности macOS.** `start-macos.sh` устанавливает зависимости Homebrew, создаёт venv, запускает настройку и стартует uvicorn на порту `7860`, поскольку AirPlay часто занимает `7000`. Использует llama.cpp/Ollama для Metal. vLLM/SGLang доступны только для CUDA/ROCm и не работают на macOS. Модели только для MLX не обслуживаются Odysseus.

### Нативная установка Windows

**Однокомандный лаунчер** (создаёт venv, устанавливает зависимости, запускает настройку, стартует сервер; безопасно для повторного запуска):

```powershell
git clone https://github.com/pewdiepie-archdaemon/odysseus.git
cd odysseus
powershell -ExecutionPolicy Bypass -File .\launch-windows.ps1
```

Или сделайте это вручную:

```powershell
git clone https://github.com/pewdiepie-archdaemon/odysseus.git
cd odysseus
py -3.11 -m venv venv
venv\Scripts\Activate.ps1
pip install -r requirements.txt
python setup.py
python -m uvicorn app:app --host 127.0.0.1 --port 7000
```

Если `python` указывает на более старую версию интерпретатора, используйте `py -3.12` (или другую установленную версию 3.11+) для шага создания venv.

**Открытие по локальной сети/Tailscale (Windows):** лаунчер привязывается к `127.0.0.1` и **не** читает `APP_BIND` / `ODYSSEUS_HOST` из `.env`, поэтому редактирование только `.env` оставляет нативный сервер Windows на loopback. Вместо этого передайте флаг `-BindHost` лаунчера:

```powershell
powershell -ExecutionPolicy Bypass -File .\launch-windows.ps1 -BindHost 0.0.0.0
```

Ручная команда `uvicorn` принимает тот же адрес как `--host 0.0.0.0`. Привязывайте вне loopback только для доверенной локальной сети/VPN, такой как Tailscale: поддерживайте `AUTH_ENABLED=true` и не exposesьте порт напрямую в публичный интернет.

**Требования:** Python 3.11+. Основное приложение (чат, агент, память, документы, электронная почта, календарь, глубокое исследование) работает полностью нативно. Для полной фоновой загрузки моделей Cookbook и инструмента shell агента также установите [Git for Windows](https://git-scm.com/download/win) (предоставляет `bash.exe`). Локальное GPU-обслуживание vLLM/SGLang требует Linux/WSL2; для локальной модели на Windows [Ollama](https://ollama.com/download) — самый простой путь — укажите Odysseus на `http://localhost:11434/v1` в настройках.

Откройте `http://localhost:7000`, войдите с помощью сгенерированного пароля администратора и настройте всё остальное в разделе **Настройки**.

## Устранение неполадок и расширенная настройка

### `chromadb-client` конфликтует со встроенным ChromaDB
Если `chromadb-client` (лёгкий пакет только для HTTP) установлен вместе с полным пакетом `chromadb`, Odysseus запускается, но ChromaDB молча переходит в режим только HTTP и завершается неудачей.

**Исправление:** удалите `chromadb-client` и принудительно переустановите полный пакет:
```bash
./venv/bin/pip uninstall chromadb-client -y
./venv/bin/pip install --force-reinstall chromadb
```

### HTTPS + локальная сеть/Tailscale
Для доступа к Odysseus по локальной сети или Tailscale с HTTPS:
1. Измените адрес привязки на `0.0.0.0` в `.env` (`APP_BIND=0.0.0.0` или `ODYSSEUS_HOST=0.0.0.0`).
2. Сгенерируйте локально доверенный сертификат для ваших IP-адресов локальной сети/Tailscale с помощью [mkcert](https://github.com/FiloSottile/mkcert):
   ```bash
   mkcert -install
   mkcert -cert-file cert.pem -key-file key.pem 192.168.1.100 tailscale-ip
   ```
3. Запустите `uvicorn` с сгенерированными сертификатами:
   ```bash
   python -m uvicorn app:app --host 0.0.0.0 --port 7000 --ssl-certfile=cert.pem --ssl-keyfile=key.pem
   ```
4. Установите CA mkcert на любое другое устройство, с которого вы хотите получить доступ к Odysseus (например, для iOS отправьте `rootCA.pem` себе по электронной почте, установите профиль и доверьте ему в настройках доверия сертификатов).

### Необязательные зависимости
`requirements-optional.txt` содержит пакеты, расширяющие функциональность. Он не устанавливается по умолчанию.

| Пакет | Расширяемая функция |
|---------|-----------------|
| `faster-whisper` | Локальное распознавание речи (микрофон -> текст) через провайдер STT "local". |
| `ddgs` | DuckDuckGo как опция провайдера поиска. |
| `PyMuPDF` | Отрисовка страниц PDF в боковой панели просмотра и заполнение форм. (Примечание: AGPL-3.0) |
| `markitdown` | Извлечение текста из документов Office/EPUB (конвертирует .docx/.xlsx/.pptx/.xls/.epub в Markdown). |

### Быстрая и воспроизводимая установка с uv (необязательно)
[uv](https://docs.astral.sh/uv/) работает как замена шагов venv + pip в руководствах по нативной установке, изменения проекта не требуются, но этот вариант обеспечивает более быструю установку и файл блокировки для воспроизводимых окружений. После [установки `uv`](https://docs.astral.sh/uv/getting-started/installation/) используйте:

```bash
uv venv venv --python 3.13
uv pip install -r requirements.txt
# затем продолжайте как обычно: python setup.py, uvicorn, ...
```

`requirements.txt` намеренно не фиксирует версии, поэтому две установки в разное время могут дать разные версии пакетов. Если вам нужно воспроизводимое окружение (например, между вашими машинами или для отката после неудачного обновления), сделайте снимок и восстановите точные версии с помощью:

```bash
uv pip compile requirements.txt -o requirements.lock   # снимок текущего разрешения
uv pip sync requirements.lock                          # воспроизвести его точно позже
```

`requirements.lock` добавлен в gitignore и специфичен для платформы (компилируйте его на ОС, куда разворачиваете). Перегенерируйте его намеренно, когда захотите обновить зависимости. Обычный `uv pip install -r requirements.txt` продолжает следовать незафиксированным требованиям, как и pip.

### Outlook / Office 365
Учётные записи электронной почты Odysseus в настоящее время используют аутентификацию IMAP/SMTP по имени пользователя и паролю. Outlook и Microsoft 365 обычно требуют OAuth вместо этого, поэтому обычные пароли почтовых ящиков Microsoft не сработают. См. [docs/email-outlook.md](../en/email-outlook.md) для текущего ограничения и планируемого направления интеграции.

## Примечания по безопасности
Odysseus — это самоподдерживаемое рабочее пространство с мощными локальными инструментами: доступ к shell, загрузка файлов, скачивание моделей, веб-исследование, интеграции с электронной почтой/календарём и API-токены. Обращайтесь с ним как с панелью администратора.

- Поддерживайте `AUTH_ENABLED=true` для любого сетевого развёртывания.
- Поддерживайте `LOCALHOST_BYPASS=false` вне локальной разработки.
- Используйте `SECURE_COOKIES=true`, когда Odysseus обслуживается через HTTPS доверенным обратным прокси или шлюзом приватного доступа.
- Не exposeйте его напрямую в публичный интернет без HTTPS и доверенного обратного прокси или слоя приватного доступа.
- Не включайте `.env`, `data/`, `logs/`, базы данных, загрузки, сгенерированные медиафайлы, резервные копии, файлы аутентификации/сессий, ключи API и токены провайдеров/моделей в Git и общие ресурсы. По умолчанию они игнорируются.
- Просмотрите `data/auth.json` после первого запуска: отключите открытую регистрацию, если она вам не нужна, назначьте администратором только свою учётную запись и не давайте демо/тестовым учётным записям права администратора.
- Пользователи без прав администратора по умолчанию не получают доступ к shell/Python/чтению/записи файлов, а маршруты/инструменты только для администраторов, такие как управление MCP, API-токены, вебхуки, обслуживание моделей/Cookbook, резервное копирование/хранилище и настройки приложения, доступны только администраторам. Другие функции управляются привилегиями отдельных пользователей, поэтому проверяйте привилегии каждого пользователя перед развёртыванием.
- Ротируйте любые API-ключи или токены, которые когда-либо вставлялись в общий чат, демо, скриншот или лог.
- Если вы включаете API-токены или вебхуки, создавайте отдельные токены для каждой интеграции и удаляйте неиспользуемые.
- Предпочитайте привязку ручных запусков разработки к `127.0.0.1`; привязывайте к `0.0.0.0` только когда вам намеренно нужен доступ по локальной сети/обратному прокси.
- Держите ChromaDB, SearXNG, ntfy, Ollama, vLLM, llama.cpp, базы данных и прямые API провайдеров/моделей только для внутреннего доступа. Exposeйте только аутентифицированную точку входа Odysseus web/API через ваш доверенный прокси или слой приватного доступа.
- Перед публикацией форка запустите `git status --short` и убедитесь, что ни один приватный файл из `.env`, `data/`, `logs/`, загрузок, резервных копий или локальных баз данных не добавлен в индекс.

### Приватные развёртывания или развёртывания через прокси
Odysseus предоставляет обычный HTTP на своём порту приложения. Docker Compose по умолчанию привязывает Odysseus и встроенные сервисы к `127.0.0.1`, поэтому типичная настройка для приватного/продакшн-развёртывания:

1. Держите Odysseus на localhost, например `127.0.0.1:7000`.
2. Завершайте HTTPS на доверенном обратном прокси или шлюзе приватного доступа.
3. Размещайте аутентифицированную точку входа Odysseus web/API за этим слоем.
4. Держите прямые порты сервисов и моделей только для внутреннего доступа.

Cloudflare Access, Tailscale, Caddy, nginx и Traefik — все подходят под эту схему; Odysseus не требует ни одного из них. Если ваш слой доступа достигает Odysseus на том же хосте, проксируйте на `http://127.0.0.1:7000` и поддерживайте `AUTH_ENABLED=true`, `LOCALHOST_BYPASS=false` и `SECURE_COOKIES=true`.
`ALLOWED_ORIGINS` перечисляет точные разрешённые источники для кросс-доменных браузерных/API-клиентов; обычный одноимённый доступ через обратный прокси обычно не требует специальной записи CORS.

Типичные порты только для внутреннего доступа из стандартной конфигурации docs/compose:

| Порт | Сервис |
|---|---|
| `7000` | Прямой порт приложения Odysseus |
| `8080` | SearXNG |
| `8091` | ntfy |
| `8100` | Порт хоста ChromaDB для ручного/compose доступа |
| `11434` | Ollama |
| `8000-8020` | Типичные локальные API моделей/провайдеров |

### Встроенные MCP-серверы (необязательная настройка)

Odysseus автоматически регистрирует несколько встроенных MCP-серверов при запуске. Основанные на npx (в настоящее время сервер браузера `@playwright/mcp`) запускаются только когда их npm-пакет уже находится в локальном кэше npx. Если пакет не закэширован, сервер пропускается с сообщением в логе запуска о том, что делать, поэтому свежая установка не блокируется на многоминутной загрузке npm или зависает при отсутствии системных зависимостей Playwright.

Для включения браузерного MCP (навигация по страницам, скриншоты, просмотр) выполните однажды:

```bash
npx -y @playwright/mcp@latest --version
```

Это установит `@playwright/mcp` и Playwright (около 300 МБ). Перезапустите Odysseus, и сервер зарегистрируется при запуске.
